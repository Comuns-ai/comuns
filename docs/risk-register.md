## 1 Summary

Comuns is a community proposal for open-source decentralized LLM **inference only**. Nothing runs yet. This register consolidates proposed failure modes, required controls and residual risks; no row records a completed check. The project plan orders the work and the normative source paths define behavior. This register grants no implementation, deployment, spending or mainnet authority.

Settlement targets Arbitrum One Solidity/EVM; Stylus is not v1, with new activations recorded paused since 2026-10-02 (evidence register §1 [V]). The Rust node runs off-chain through llama.cpp C/C++ kernels initially (evidence register §3 [V]). Ordinary jobs use HPKE both ways, but the executing node sees plaintext in standard mode. Attested mode is optional and weak against physical attack (evidence register §4 [L]); verifiable mode means user-chosen second-node re-execution under a demonstrated deterministic profile, with another disclosed full-prompt reader. Strict owner-only confidentiality against the chosen remote node remains unmet.

Any node may offer any registered model it can load. Hardware classes S < M < L < X select ordered price bands and never gate model tiers; per-class benchmark bars establish a class, while maxTier is separate and informational. Bands cover every tier/class pair for input and output, with each higher-class floor strictly above the preceding ceiling. No wei values are adopted here. Models are registered and updated only by the governance timelock through CIPs; no seated maintainers means no mainnet registration.

ETH session escrow uses chunked cumulative vouchers of the canonical type defined in docs/protocol/contracts-and-settlement.md, including outputCommitment. Protocol fee 0 is not L2 gas; there is no token, no v1 slashing, and a signed voucher is not reversed. Settlement, refund and bond release credit balances; only withdraw() sends ETH. Collective answers are not verification and never affect payment. Comuns never claims to be cheaper than hosted APIs. Code and documents are Apache-2.0 with DCO and no CLA. CIPs have a 14-day Last Call under GOVERNANCE.md; proposal rights never depend on hardware, stake or tokens. No maintainers are seated.

Single-node execution is the default. Every multi-node feature — collective_answer, parallel_planning, task_decomposition, model_sharding and cross_node_speculation — and the optional orchestrator node is opt-in per request and disclosed on the disclosure sheet. The reader list is a floor derived from actual payloads, counted by distinct node and distinct operator: executor, verifier, answerers, reviewers, remote synthesizers, planners and plan reviewers, plan synthesizers, draft and target, every shard holder, remote assessors, merge nodes, and orchestrator nodes whenever they plan, merge or synthesize. Sub-task executors and reviewers count unless the client verifies their payload contains no prompt text; assume merge inputs quote the prompt. counts.fullPrompt counts literal full-prompt deliveries; readersOfFullPrompt is at least that count and supplies the banner. Consent does not prevent a selected recipient copying plaintext.

The chain stores offers and sessions, never plans or pool lists. sessionSigner stays on the user's client in v1. Phase 1 is a single-node Sepolia session with one model, standard mode, no collective answer, no sharding, no cross-node speculative decoding, no TEE, no verifiable mode and no slashing. Phase 2 adds contexts, classes, pools, the full sheet and client-side orchestration. Sharding and cross-node speculative decoding are separately gated experimental Phase 3 spikes; the reference client refuses both under mainnet parameters. Every shard holder is unpaid and has no session or voucher, including first and last. Dedicated later CIPs are required for activation metering or signer delegation. Negative spike results do not disable collective answers or decomposition.

## 2 Method

Severity is a proposed impact assessment, not measured likelihood: **High** means loss of funds, disclosure outside consent, unsafe authority or failure of a core release condition; **Medium** means bounded loss, degraded availability, material cost or a recovery burden; **Low** means localized inconvenience with a straightforward recovery. A High residual can remain after its controls pass; severity is not a claim that an event has occurred.

**Release-blocking = yes** means the closure evidence in section 4 is required before the named surface is exercised or released. Mainnet consideration requires all baseline closures plus the go/no-go process. Feature-specific rows can be satisfied by proving that the optional feature stays unavailable; a negative Phase 3 result is valid closure when accompanied by enforced exclusion. An inherent risk such as executor plaintext is closed for this gate only by correct boundaries and honest consent, never by pretending to eliminate it. A no row remains tracked and disclosed; any newly discovered defect violating a mandatory invariant still blocks release. Document-only work can proceed while software gates remain unmet.

Evidence citations point to the section of docs/evidence-register.md that actually contains the external fact, retaining [V], [L] or [U]. **UNVERIFIED** identifies a local feasibility, adoption or implementation assumption absent from the register. A cited external result does not validate Comuns. In §9, [V] means the networked preprint reports the result and [U] means it is not independently replicated. It promises no WAN speed-up and does not measure the plan's ordinary single-node baseline. The llama.cpp RPC warning belongs to §10. New orchestration and distribution rows use §9–§12 where relevant, or UNVERIFIED where the risk is this proposal's own assumption.

Each owning working group maintains the row and closure record through public, secret-free issues or CIPs. Ownership gives no merge or parameter authority. Rough consensus and residual acceptance are written down. The binding review decisions take precedence over older source wording; this register does not invent new protocol functions, prices, metering or stronger assurances. All gates below remain **unverified** until future implementation and review supply evidence.

## 4 Release gates

The following restates **every blocking row** as an observable closure condition. These are proposed checks, not results. The general software-publication prerequisite in RR-15 applies in all phases; placing external review in Phase 4 never defers the monitored private-channel requirement. Gate evidence must contain no real prompts, keys or seed phrases.

| Blocking row | Required closure evidence |
|---|---|
| RR-01 | Before Phase 1 use, demonstrate two-way sealing and pre-signature executor disclosure; never describe remote standard mode as owner-only. |
| RR-02 | Before enabling attested mode, demonstrate quote/key checks and explicit physical-access disclosure; otherwise leave the mode unavailable. |
| RR-03 | Before enabling verifiable mode or spot checks, demonstrate prior reader consent, local comparison and no commitment disclosure to undisclosed third parties. |
| RR-05 | Before the Sepolia payment exit, prove per-session node credits plus refund equal depositWei and escrow ETH equals credited balances plus open/closing deposits minus settledWei; test rejecting recipients and independent review before mainnet consideration. |
| RR-08 | Before mode 2 is advertised, publish its demonstrated profile and repeatability evidence; otherwise publish a negative result and disable that mode, never claim a false success. |
| RR-09 | Before Phase 2 exit, test version-scoped decryption, re-wrap, event-history hashes, race/rebase, keyring rotation and restore with surviving ciphertext; show distinct key-loss and blob-loss outcomes. |
| RR-10 | Before model use, verify exact-file terms and authorized registration; before Phase 4 exit, complete model-license review and canonical LICENSE comparison, keeping Apache-2.0, DCO and no CLA. |
| RR-11 | Before release consideration, demonstrate outage handling and publish the window-sizing rationale and late-outage residual; finalize must never be presented as node payment. |
| RR-12 | Before a mainnet go/no-go, resolve the upgrade model and execution authority by CIP, with independent review of escrow and funded-session protections. |
| RR-14 | Before exercising authority, show the Final CIP record and proper lifecycle; no hardware, stake or token condition may weight proposal rights. |
| RR-15 | Before any software release, demonstrate seated authority and a monitored private security channel under SECURITY.md; missing capacity cannot be waived by an informal assignment. |

The settlement gate must distinguish the three operations: redeemVoucher credits only the node, closeWithVoucher credits the node and remaining user refund, and finalize credits only the remainder to the user. In each payout, update settledWei before computing any refund. Credits are collected only with withdraw(), never pushed during settlement. Cooperative closure needs a final voucher; an absent client calls for highest non-final redemption while legal, closeSession, then finalize after closeDeadline. A client without its voucher log signs nothing and uses only unilateral closure. Nothing closes automatically, closeSession does not revoke a stolen signer, and a lost wallet cannot withdraw its credits.

The cryptography gate must demonstrate sessionSigner-signed job envelopes with response keys and job parameters encrypted and authenticated; node-signed input receipts before prefill checked against the pinned tokenizer and last signed totals; random per-version context keys and wallet-signed exact-range grants; and the canonical cumulative voucher with outputCommitment. The session commitKey is random and sent sealed in the first job, not derived from a per-job exporter; its transcript chain spans every job and each commitment uses its own voucher seq. It is retained with the node's encrypted persistent transcript and highest voucher until settlement. Opening it discloses session output and does not create an on-chain proof. Receipt hashes stay sealed; hashes outside encryption are keyed. TLS does not hide traffic sizes or timing.

Disclosure closure requires the normative sheet JSON and all generated UI to agree. Any node, model, data-scope, price, cap or reader change, any new session and any later request using an existing session requires confirmation before its jobs or signatures. An optional orchestrator never holds sessionSigner. Sessions are indexed by (node, modelId); jobs share one cumulative chain sequentially within each session. Extra parallel sessions require their own disclosed caps. All copies of the sheet must distinguish literal payload counts from nodes able to read the prompt. An undisclosed reader is never made acceptable by a good synthesis score.

For experimental closure, narrow each spike to its specified mechanics rather than filling design gaps with promises. In sharding the client mediates every stage, holds embeddings, forwards activations, samples from last-stage logits and caches stage inputs; mutual TLS is bound to registered operator keys. Lost holders default to a restart on a confirmed chain; replay to a disclosed replacement may be measured with its latency, storage and privacy cost. No holder gets a session. In speculation rounds stay within one job on each node, with accepted tokens and a rollback point; prompt input is billed once per job. Draft distributions are sealed metadata and never tokens, or the experiment is narrowed to greedy decoding with demonstrated local determinism. The greedy-decoding exact-match check counts a mismatch as a preservation failure only outside the measured run-to-run variation of that target build (evidence register §5, [V]: 80 unique outputs in 1,000 temperature-0 runs without batch-invariant kernels); a byte-identical claim is never accepted without that measurement. The target scores at most MAX_DRAFT_TOKENS per round and its testnet session bills drafted tokens scored. Correction-token and continuation accounting remain entry gaps. No WAN speed-up is promised, neither feature runs on mainnet, and neither is verification.

Phase 4 must add independent contract and cryptography review by people who did not write those components, license confirmation, recorded residuals and the public Arbitrum One go/no-go CIP. All forty directional bands and seated governance remain separate mainnet prerequisites. Passing this table or completing a testnet milestone provides no mainnet authorization.

## 5 Open questions

- What evidence should close a control gate while preserving an explicit High residual, especially executor confidentiality, physical-access attestation and sequencer deadline loss?
- What independent measurements establish useful class S participation and viable offers from high-performance providers under all ordered bands?
- Which deterministic profiles can be demonstrated on the chosen engines, and which optional modes should remain unavailable after a negative result?
- What exact shard-chain client credential, certificate binding, compatible partition format and replay-cache policy can the Phase 3 spike support?
- How will speculative round frames encode distributions, score receipts, correction tokens and continuation work without confusing metadata with tokens or re-billing the prompt?
- How should future CIPs handle signer rotation/revocation, bounded delegation, component metering, withdrawal recipients and an anyone-can-close idle timeout? None is a v1 facility.
- How should the community publish private-prompt-set benchmark evidence, operator-diversity information and reputation events without leaking prompts or implying a proof of honesty?
- Which backup format and storage-availability checks let users distinguish a recoverable key loss from irretrievable ciphertext loss?
- What minimum evidence should the go/no-go CIP require when some optional features are excluded and the remaining risks cannot be eliminated?
