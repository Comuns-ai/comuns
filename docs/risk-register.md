## 1 Summary

Comuns is a community proposal for open-source decentralized LLM **inference only**. Nothing runs yet. This register consolidates proposed failure modes, required controls and residual risks; no row records a completed check. The project plan orders the work and the normative source paths define behavior. This register grants no implementation, deployment, spending or mainnet authority.

Settlement targets Arbitrum One Solidity/EVM; Stylus is not v1, with new activations recorded paused since 2026-10-02 (evidence register §1 [V]). The Rust node runs off-chain through llama.cpp C/C++ kernels initially (evidence register §3 [V]). Ordinary jobs use HPKE both ways inside Oblivious HTTP. In standard mode the chosen node can read the prompt and should not learn who asked; an anonymous credit funds the session and the chain stores no payer. Attested mode is opt-in: the node should not be able to read the prompt either, barring a physical attack (evidence register §14). Verifiable mode means user-chosen second-node re-execution under a demonstrated deterministic profile, with another disclosed full-prompt reader. Local execution is not a product option. Inference runs only on network nodes.

Any node may offer any registered model it can load. Hardware classes S < M < L < X select ordered price bands and never gate model tiers; per-class benchmark bars establish a class, while maxTier is separate and informational. Bands cover every tier/class pair for input and output, with each higher-class floor strictly above the preceding ceiling. No wei values are adopted here. Models are registered and updated only by the governance timelock through CIPs; no seated maintainers means no mainnet registration.

ETH session escrow uses chunked cumulative vouchers of the canonical type defined in docs/protocol/contracts-and-settlement.md, including outputCommitment. Protocol fee 0 is not L2 gas; there is no token, no v1 slashing, and a signed voucher is not reversed. Settlement, refund and bond release credit balances; only withdraw() sends ETH. A credit session records `user = address(0)`. On a credit session, `redeemVoucher` and `closeWithVoucher` split each incremental payout between the relay and the node, and `closeWithVoucher` and `finalize` record `pendingWei = depositWei − settledWei` instead of crediting a user. `claimChange` returns that value as fresh notes, with dust to the node. The reference client does not offer wallet `openSession` as a privacy mode. Collective answers are not verification and never affect payment. Comuns never claims to be cheaper than hosted APIs. Code and documents are Apache-2.0 with DCO and no CLA. CIPs have a 14-day Last Call under GOVERNANCE.md; proposal rights never depend on hardware, stake or tokens. No maintainers are seated.

Single-node execution is the default. Every multi-node feature — collective_answer, parallel_planning, task_decomposition, model_sharding and cross_node_speculation — and the optional orchestrator node is opt-in per request and disclosed on the disclosure sheet. The reader list is a floor derived from actual payloads, counted by distinct node and distinct operator: executor, verifier, answerers, reviewers, remote synthesizers, planners and plan reviewers, plan synthesizers, draft and target, every shard holder, remote assessors, merge nodes, and orchestrator nodes whenever they plan, merge or synthesize. Sub-task executors and reviewers count unless the client verifies their payload contains no prompt text; assume merge inputs quote the prompt. counts.fullPrompt counts literal full-prompt deliveries; readersOfFullPrompt is at least that count and remains visible beside the headline. The headline uses counts.operatorReadable and separately describes counts.attestedRecipients with the attested assurance. Consent does not prevent a selected recipient copying plaintext.

The chain stores offers and sessions, never plans or pool lists. ContextRegistry stores no owner: a context is keyed by contextId, and grants are signed by the context key, not the wallet. sessionSigner is a fresh key per session, stays on the user's client, and is never reused across sessions. Every session-specific chain read by the reference client goes through a relay. An indexer is a backend behind that transport, not an alternative to it. Phase 1 is a single-node Sepolia credit session with one model and standard mode, through a relay distinct from the node, with at least two testnet-only denominations whose values are unset. It includes no collective answer, no sharding, no cross-node speculative decoding, no TEE, no verifiable mode and no slashing. The Phase 1 exit demonstrates a partial spend with claimChange into at least one smaller note plus dust, a zero-use session claimed back in full, and a ragequit. Phase 2 adds contexts, classes, pools, the full sheet and client-side orchestration. Sharding and cross-node speculative decoding are separately gated experimental Phase 3 spikes; the reference client refuses both under mainnet parameters. Every shard holder is unpaid and has no session or voucher, including first and last. In that spike the client does not compute embeddings or the output layer; those run on disclosed network nodes, and activations reach each holder through a relay. Dedicated later CIPs are required for activation metering or signer delegation. Negative spike results do not disable collective answers or decomposition.

## 2 Method

Severity is a proposed impact assessment, not measured likelihood: **High** means loss of funds, disclosure outside consent, unsafe authority or failure of a core release condition; **Medium** means bounded loss, degraded availability, material cost or a recovery burden; **Low** means localized inconvenience with a straightforward recovery. A High residual can remain after its controls pass; severity is not a claim that an event has occurred.

**Release-blocking = yes** means the closure evidence in section 4 is required before the named surface is exercised or released. Mainnet consideration requires all baseline closures plus the go/no-go process. Feature-specific rows can be satisfied by proving that the optional feature stays unavailable; a negative Phase 3 result is valid closure when accompanied by enforced exclusion. An inherent risk such as executor plaintext is closed for this gate only by correct boundaries and honest consent, never by pretending to eliminate it. A no row remains tracked and disclosed; any newly discovered defect violating a mandatory invariant still blocks release. Document-only work can proceed while software gates remain unmet.

Evidence citations point to the section of docs/evidence-register.md that actually contains the external fact, retaining [V], [L] or [U]. **UNVERIFIED** identifies a local feasibility, adoption or implementation assumption absent from the register. Rows RR-39 through RR-47 cite §14–§16 with the annex mark, or UNVERIFIED where the risk is this proposal's own assumption. A Semaphore audit does not transfer to the Comuns wrapper. Items in §16 are facts, not legal advice and not a classification of Comuns. A cited external result does not validate Comuns. In §9, [V] means the networked preprint reports the result and [U] means it is not independently replicated. It promises no WAN speed-up and does not measure the plan's ordinary single-node baseline. The llama.cpp RPC warning belongs to §10. New orchestration and distribution rows use §9–§12 where relevant, or UNVERIFIED where the risk is this proposal's own assumption.

Each owning working group maintains the row and closure record through public, secret-free issues or CIPs. Ownership gives no merge or parameter authority. Rough consensus and residual acceptance are written down. The binding review decisions take precedence over older source wording; this register does not invent new protocol functions, prices, metering or stronger assurances. All gates below remain **unverified** until future implementation and review supply evidence.

The settlement gate must distinguish wallet sessions from credit sessions. On a wallet session, redeemVoucher credits only the node, closeWithVoucher credits the node and the remaining user refund, and finalize credits only the remainder to the user. On a credit session, each incremental payout splits the relay's share to balances[relay] and the rest to balances[node], and closeWithVoucher and finalize record pendingWei equal to depositWei minus settledWei instead of crediting a user. claimChange then inserts fresh notes and sends dust to the node. In each payout, update settledWei before computing any refund or pendingWei. Balances are collected only with withdraw(), never pushed during settlement. A wallet session's cooperative closure needs a final voucher; an absent client calls for highest non-final redemption while legal, closeSession, then finalize after closeDeadline. A credit session is closed by the node, or by any broadcaster presenting a sessionSigner signature over (chainId, escrow, sessionId, "close"). The reference client submits that through a relay or broadcaster, never from the deposit wallet. Close is not permissionless. If both the node and the sessionSigner key are gone, the credit session stays open. A client without its voucher log signs nothing further and uses only that closure path. Nothing closes automatically, closeSession does not revoke a stolen signer, and on the wallet path a lost wallet cannot withdraw its credits.

The cryptography gate must demonstrate sessionSigner-signed job envelopes with response keys and job parameters encrypted and authenticated; node-signed input receipts before prefill checked against the pinned tokenizer and last signed totals; random per-version context keys and exact-range grants signed by the context key, not the wallet, with no owner stored on the chain; and the canonical cumulative voucher with outputCommitment. The session commitKey is random and sent sealed in the first job, not derived from a per-job exporter; its transcript chain spans every job and each commitment uses its own voucher seq. It is retained with the node's encrypted persistent transcript and highest voucher until settlement. Opening it discloses session output and does not create an on-chain proof. Receipt hashes stay sealed; hashes outside encryption are keyed. TLS and OHTTP do not hide traffic sizes or timing. Padding to unset size buckets reduces that leak and does not remove it (RR-43; evidence register §16, [V]).

Disclosure closure requires the normative sheet JSON and all generated UI to agree. Any node, model, data-scope, price, cap or reader change, any new session and any later request using an existing session requires confirmation before its jobs or signatures. An optional orchestrator never holds sessionSigner. Sessions are indexed by (node, modelId); jobs share one cumulative chain sequentially within each session. Extra parallel sessions require their own disclosed caps. All copies of the sheet must distinguish literal payload counts from nodes able to read the prompt. An undisclosed reader is never made acceptable by a good synthesis score.

For experimental closure, narrow each spike to its specified mechanics rather than filling design gaps with promises. In sharding the client keeps transport, orchestration and sampling decisions only. Embedding and output-layer computation run on disclosed network nodes, which are unpaid volunteer readers like the other holders. Activations to each shard holder travel through a relay, OHTTP-encapsulated to that holder's registered ohttpKeyConfig, with no inner job HPKE envelope. No direct client-to-holder connection skips the relay. Lost holders default to a restart on a confirmed chain; replay to a disclosed replacement may be measured with its latency, storage and privacy cost. No holder gets a session. The unpaid sharding spike is exempt from the rule that every paid recipient has a credit session. In speculation rounds stay within one job on each node, with accepted tokens and a rollback point; prompt input is billed once per job. Draft distributions are sealed metadata and never tokens, or the experiment is narrowed to greedy decoding with demonstrated local determinism. The greedy-decoding exact-match check counts a mismatch as a preservation failure only outside the measured run-to-run variation of that target build (evidence register §5, [V]: 80 unique outputs in 1,000 temperature-0 runs without batch-invariant kernels); a byte-identical claim is never accepted without that measurement. The target scores at most MAX_DRAFT_TOKENS per round and its testnet session bills drafted tokens scored. Correction-token and continuation accounting remain entry gaps. No WAN speed-up is promised, neither feature runs on mainnet, and neither is verification.

Phase 4 must add independent contract and cryptography review by people who did not write those components, including the Semaphore-integration review in the RR-41 gate. That review does not transfer Semaphore's audits to the Comuns wrapper. It also records license confirmation, the residuals in this register, and the public Arbitrum One go/no-go CIP. Regulatory classification is UNVERIFIED and is a Phase 4 review item (facts in evidence register §16, not legal advice). All forty directional bands and seated governance remain separate mainnet prerequisites. Passing this table or completing a testnet milestone provides no mainnet authorization.

## 5 Open questions

- What evidence should close a control gate while preserving an explicit High residual, especially executor confidentiality, physical-access attestation and sequencer deadline loss?
- What independent measurements establish useful class S participation and viable offers from high-performance providers under all ordered bands?
- Which deterministic profiles can be demonstrated on the chosen engines, and which optional modes should remain unavailable after a negative result?
- What exact shard-chain client credential, relay and ohttpKeyConfig binding, compatible partition format and replay-cache policy can the Phase 3 spike support? There is no direct client-to-holder connection.
- How will speculative round frames encode distributions, score receipts, correction tokens and continuation work without confusing metadata with tokens or re-billing the prompt?
- How should future CIPs handle signer rotation or revocation, including a stolen sessionSigner that can still sign vouchers until settlement and claimChange with no deadline while pendingWei is above zero, plus bounded delegation, component metering, withdrawal recipients and an anyone-can-close idle timeout? None is a v1 facility. Close of a credit session is not permissionless.
- What observed group size should make the client warn, given that no authoritative minimum anonymity-set size was found (evidence register §15, [U]) and no threshold is adopted?
- Which padding-bucket and token-batch sizes are worth their bandwidth, given that they reduce and do not remove traffic analysis (evidence register §16, [V]) and no sizes are adopted?
- How should the community publish private-prompt-set benchmark evidence, operator-diversity information and reputation events without leaking prompts or implying a proof of honesty?
- Which backup format and storage-availability checks let users distinguish a recoverable key loss from irretrievable ciphertext loss?
- What minimum evidence should the go/no-go CIP require when some optional features are excluded and the remaining risks cannot be eliminated?
