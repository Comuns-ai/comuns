---

Comuns is a community proposal for open-source, decentralized LLM inference settled in ETH on Arbitrum One. Nothing described here runs yet. No maintainer is seated, no price in wei is adopted, and mainnet is not deployable. Each answer points at the document that owns the detail. Amounts a person would see in the app are shown in ETH with the unit. This proposal does not claim a lower price or a stronger proof than a hosted API or than any other network.

### Can the node operator read my prompt?

Yes, in standard mode. The chosen node can read the prompt in standard mode, and it can read the granted context and the completion as well, because it decrypts them to run the model. The client says so on the disclosure sheet before you sign. Attested mode still shows the prompt in plaintext inside the TEE; the client checks a quote first, the request fails closed if no eligible node exists, and attested mode is not a physical-attack defense (evidence register §4, [L]). Verifiable mode adds a second, user-chosen node that re-executes the prompt under a demonstrated deterministic profile, so that verifier can read the prompt too, and the session's mode is public on-chain. The only option in which nobody but you reads the prompt is to run the model on your own machine. The default is one node. See [security/privacy-and-contexts.md](security/privacy-and-contexts.md) and [security/inference-verification.md](security/inference-verification.md).

### Do I need a GPU?

You do not need a GPU to send a prompt. A remote node runs the model. An operator's machine has to load the model it offers. The illustrative picture of class S includes a CPU-only machine, and that picture is not a measured minimum and not a serving cap. A class is a price band, decided by passing per-class benchmark bars, and it does not decide which model a machine may offer. Whether a model fits is the operator's own check of memory. No benchmark has been run by this project. See [node/hardware-classes-and-benchmarks.md](node/hardware-classes-and-benchmarks.md).

### What does a request cost, and why does this proposal not claim to be cheaper than a hosted API?

There is no adopted price. Bands are empty until a CIP sets them, so a mainnet session cannot be opened yet. When a session exists, the inference payment is ETH for tokens:

`paymentWei = (priceInPerMillion * inputTokens + priceOutPerMillion * outputTokens) / 1000000`

with the session's prices and integer floor division. The sheet shows that amount in ETH, and it shows L2 gas in ETH beside it, as a separate estimate. This proposal does not claim to be cheaper than a hosted API. L2 gas is extra and goes to the chain. The band rule makes a stronger hardware class charge more than a weaker class for the same model. Evidence register §6 records much higher aggregate tokens per second for batched datacenter runs than for single-stream runs ([V]); a claim that the batched token is therefore cheaper to produce on a matched machine is derived and UNVERIFIED. An opt-in request that uses several nodes pays one ordinary session per distinct pair of node and model id, so it costs more sessions, not fewer. The protocol fee is 0. Illustrative fixtures are not offers. After you confirm a sheet, `openSession` reverts if the node's offer no longer matches the prices you confirmed, and the client still re-reads the prices copied on-chain and signs nothing if they differ. See [economics/cost-and-pricing.md](economics/cost-and-pricing.md) and [protocol/contracts-and-settlement.md](protocol/contracts-and-settlement.md).

### What is the difference between L2 gas and the inference payment?

They are two different payments. The inference payment is the ETH formula above: token counts times the session's per-million prices, credited to the node for output you acknowledged and for input you signed. L2 gas is the fee Arbitrum One charges to include a transaction, such as `openSession`, `topUp`, `redeemVoucher`, `closeWithVoucher`, `closeSession`, `finalize` or `withdraw`. Gas does not buy model tokens, and the inference cap does not cap gas. No contract pushes ETH to a wallet during settlement. The contract credits an internal balance, and `withdraw()` is the only function that sends ETH, paying the caller that caller's whole balance. See [economics/cost-and-pricing.md](economics/cost-and-pricing.md).

### Why does a session cover many messages instead of one transaction per message?

A session is how this proposal keeps chain fees from dominating a small prompt. Hosted prices for a small model start near $0.02 per million input tokens and $0.04 per million output tokens (evidence register §6, [V]). The Arbitrum One fee snapshot dated 2026-10-13 records gas at 0.02 gwei and an ERC-20 transfer near $0.003 (evidence register §1, [V]). An ETH transfer is derived near $0.001 (evidence register §1, [U]). A short prompt's inference at those hosted rates is worth far less than two contract calls, so one on-chain transaction per message would spend more on L2 fees than on that inference and would ask the wallet to sign every message. That comparison is why a session exists. It is not a claim that a session here costs less than a hosted API. One session deposits ETH once and settles once on the usual path (`openSession`, then the node's `closeWithVoucher`). Every chunk in between is an off-chain signature. A signed voucher is not reversed. You pay only the cumulative tokens you signed, up to the effective cap, which is the minimum of the deposit and the spend cap. Many jobs may share a session, one job at a time. See [protocol/contracts-and-settlement.md](protocol/contracts-and-settlement.md).

### Why Arbitrum One, and why not Stylus for v1?

Settlement is Arbitrum One, and the contracts are Solidity on the EVM. The chain records who offers which model, the hash of each context version, and the ETH session. It does not run the model. New Stylus activations are paused on Arbitrum One and Nova since 2026-10-02, with no reopening date (evidence register §1, [V]), so Stylus is not the v1 path. A dedicated chain is a later question, not a v1 plan. See [adr/0001-settle-on-arbitrum-one-evm-not-stylus.md](adr/0001-settle-on-arbitrum-one-evm-not-stylus.md).

### Why is there no token?

v1 has no protocol token, no emissions and no coin vote. Operators are paid in ETH from the session you opened. A decision is a CIP. A balance of any asset, including ARB, is not a vote on this project. The protocol fee is 0, so this proposal has no treasury. See [adr/0007-no-protocol-token-in-v1.md](adr/0007-no-protocol-token-in-v1.md) and [../GOVERNANCE.md](../GOVERNANCE.md).

### Why is the node written in Rust, and why are the kernels C and C++?

Inference runs off-chain in an open-source Rust node so the process, the meter and the voucher checks share one program. The first backend is llama.cpp through Rust bindings, and those kernels are C and C++ (evidence register §3, [V]). The second backend is mistral.rs (evidence register §3, [V]). The kernels do the math. This proposal does not claim that Rust alone makes inference faster. See [adr/0002-off-chain-rust-inference.md](adr/0002-off-chain-rust-inference.md) and [node/node-design.md](node/node-design.md).

### Why not zero-knowledge proofs for the result?

The evidence register records zero-knowledge inference costs that are not an interactive chat: on the order of under 15 minutes for a 13B model, about 174 tokens per minute for a small published model, and about 150 seconds per token for an 8B model (evidence register §5, [L]). v1 does not use those proofs as the result check. When you opt in, verifiable mode is re-execution by a second node you choose, under a demonstrated deterministic profile, and that node can read the prompt. A candidate activation checker cannot see speculative decoding and is not a substitute for re-execution (evidence register §5, [V]). A later phase may try further checks and may publish a negative result. This proposal does not rank re-execution as a stronger proof than a zero-knowledge proof. See [security/inference-verification.md](security/inference-verification.md).

### How are nodes kept honest without slashing?

v1 has no slashing. The registration bond is withdrawable after an unlock delay, and it is never seized. What you can check in every session is that you signed the voucher, that the token counts match your own tokenization, and that each chunk you paid for was delivered to you. The node sends an input receipt before prefill; you sign the input voucher only if your count matches. A node can still redeem that input voucher and never run the prompt. Your loss on that prompt is bounded by the input fee, a signed voucher is not reversed, and the remedy is to stop signing and record a reputation event. Ordinary sampling is not deterministic: 1,000 temperature-0 runs of one large model produced 80 distinct outputs (evidence register §5, [V]), so a penalty for two different outputs would hit honest nodes. A dispute is a reputation event. It is not a refund. See [security/inference-verification.md](security/inference-verification.md) and [adr/0004-sessions-vouchers-and-no-slashing.md](adr/0004-sessions-vouchers-and-no-slashing.md).

### What is a context, and how is it shared between nodes?

A context is a versioned blob your wallet owns, such as a transcript, a document or a system prompt. Each version has its own random key. The chain stores the content hash of the ciphertext blob, not the text. Shared contexts are re-wrapped ciphertext: your client seals that version's key to the node's HPKE key, and your wallet signs the grant. A second node gets its own grant. Nodes do not exchange plaintext. A narrow grant carries only the keys of the versions you named, and it expires at a unix time. The backup holds your identity key and the key-wrap records. It does not hold the ciphertext, so a blob that lived only on a lost device is gone even with the backup. Keep a context host or a second device if you need the bytes. See [security/privacy-and-contexts.md](security/privacy-and-contexts.md).

### What happens if I close my laptop in the middle of an answer?

The node can have at most one output chunk that you have not signed for, and that chunk is unpaid. If your client comes back with its voucher log, you can continue, or you can sign a final voucher and the node calls `closeWithVoucher`, which credits the node and credits your refund in one call. If the client disappears, the node redeems its highest non-final voucher while that is still legal, then calls `closeSession`. After the close deadline, `finalize` credits the remaining deposit to your address. Nothing closes a session by itself. If the voucher log is lost, the client signs nothing more on that session: you call `closeSession` directly and `finalize` after the deadline, and a replacement session needs a new sheet version because it is a new deposit. Credits sit in an internal balance until `withdraw()`. If the wallet itself is lost, that credited balance is unrecoverable, because the pull payment goes to the wallet's address. See [protocol/contracts-and-settlement.md](protocol/contracts-and-settlement.md) and [architecture/system-architecture.md](architecture/system-architecture.md).

### What happens if the sequencer is down?

Arbitrum One has a single sequencer. A transaction the sequencer ignores can be force-included through L1 after about one day, and no date is set for a decentralized sequencer (evidence register §1, [V] for the single sequencer and the force-inclusion delay; [U] for the missing date). Nodes should redeem vouchers while redemption is legal, rather than wait for the deadline. The close window is meant to be longer than an expected outage plus about one day of force inclusion. That sizing is not a guarantee: an outage that starts shortly before the close deadline can still cost the node vouchers it has not redeemed. Either you or the node may call `closeSession`. Nothing closes a session automatically. "Settled" here means the L2 has included the transaction, which is not the same as L1 finality. See [protocol/contracts-and-settlement.md](protocol/contracts-and-settlement.md).

### Which model licenses can a node host for pay?

The model registry records a license identifier and a `commercialHosting` flag. It does not grant a license. The operator who loads the weights is responsible for the right to run them and to charge for them. `openSession` and offers refuse a model whose `commercialHosting` flag is false. Examples the evidence register records: some Llama terms allow commercial use and require a separate license above a monthly-user threshold (evidence register §7, [V]); Mistral Research and Non-Production licenses forbid commercial hosting (evidence register §7, [V]); other listed weights use Apache-2.0 or MIT (evidence register §7, [V]). In v1 only the governance timelock may register a model, through a CIP. With nobody seated, there is no mainnet registration. Sepolia models would come from a testnet-only CIP. See [node/model-registry-and-licenses.md](node/model-registry-and-licenses.md).

### Is training supported?

No. Scope is LLM inference. Training, fine-tuning and federated learning are non-goals, and this proposal does not plan them. See [project-charter.md](project-charter.md).

### How do I propose a change?

Copy the CIP template and fill it in. Anyone may file a CIP, including an operator of a small machine. A CIP moves Draft, then Review, then Last Call for 14 days, then Final, if no blocking objection is open. A CIP in Last Call cannot become Stagnant. A substantive edit during Last Call returns it to Review and starts a new 14-day Last Call. One inactivity clock of 6 months applies to Draft and Review only. There is no token vote. While nobody is seated, filing a CIP does not merge it. See [../GOVERNANCE.md](../GOVERNANCE.md) and [cip/README.md](cip/README.md).

### Who controls the project today?

Nobody is seated. No maintainer has merge authority, no working group has a chair, and no ADR is adopted. The first people with merge authority have to be named by a public CIP that finishes Last Call and becomes Final. Until that day, nobody may merge, run a timelock, or take an emergency action. A name written in a draft seats nobody. ARB balances are not votes here. See [../GOVERNANCE.md](../GOVERNANCE.md) and [../MAINTAINERS.md](../MAINTAINERS.md).

### How could I run a node later?

Nothing runs yet, and this repository does not ship a node you can start today. The proposed path, once software and parameters exist, is: run the Rust node, pass the public class benchmark for a class S, M, L or X, lock the registration bond, and publish an offer only for a registered model you can actually load, with prices inside that model's band for your class and a non-zero per-model benchmark hash. The bond is withdrawable later. It is not slashed. Mainnet offers wait on seated maintainers, on a CIP that sets every band, and on governance registration of models. A testnet model waits on a testnet CIP. A self-benchmark is a claim you sign, not an unfakeable proof of the hardware. See [node/node-design.md](node/node-design.md) and [node/hardware-classes-and-benchmarks.md](node/hardware-classes-and-benchmarks.md).

### Can my node serve any model?

Yes. Any node may serve any registered model it can load. Classes price, they do not gate. `maxTier` is informational and is not a gate. The node still needs memory for the weights, a per-model self-benchmark, `commercialHosting` true, and prices inside the band for that model's tier and the node's class. A machine that cannot load a model does not offer it. Registration of the model itself is a governance act in v1, so an unregistered model cannot be offered. See [adr/0008-model-first-pools.md](adr/0008-model-first-pools.md) and [node/model-registry-and-licenses.md](node/model-registry-and-licenses.md).

### What is a model pool?

A pool is the set of nodes with a current offer `prices[modelId]` carrying a non-zero `modelBenchmarkHash`. Clients and indexers enumerate that set off-chain. A pool is not a contract and not a payee. You pay the node you chose, through an ordinary session. Any node may serve any model it can load, and `maxTier` is informational. A thin pool may have one node, or no quote inside a band. The client says so. It does not silently switch you to another model. See [adr/0008-model-first-pools.md](adr/0008-model-first-pools.md) and [protocol/contracts-and-settlement.md](protocol/contracts-and-settlement.md).

### How do I choose between a cheap small node and an expensive strong node for the same model?

You pick the model first. Every node that currently offers it is in that model's pool, whatever its class. The class selects the band, and the next stronger class must charge more than the previous class's ceiling for the same model, so a small node is the cheaper quote and a strong node is the dearer quote when both offers are inside their bands. You can also sort by measured speed, reputation and privacy mode. Measured speed is a published claim plus whatever your client observes. A spot re-benchmark uses a private prompt set at a random time, and it is still not an unfakeable proof. The sheet shows the two prices and the cap in ETH before you sign. See [economics/cost-and-pricing.md](economics/cost-and-pricing.md) and [node/hardware-classes-and-benchmarks.md](node/hardware-classes-and-benchmarks.md).

### Do several nodes see my prompt?

The default is one node. That one node can read the prompt in standard mode. Every multi-node execution feature is opt-in per request. The features are collective answers, parallel planning, task decomposition, and the experimental spikes for model sharding and cross-node speculation. The sheet shows which nodes read what: role, payload, mode, prices and cap, and a count of nodes and of operators that can read the full prompt. That count is a floor taken from the actual payloads, not a ceiling. Consent on an earlier request is not consent for this one. If the pool cannot fill the set you confirmed, the request fails closed. It does not quietly drop back to fewer nodes. See [security/privacy-and-contexts.md](security/privacy-and-contexts.md) and [protocol/orchestration.md](protocol/orchestration.md).

### What is a collective answer, what does it cost, and when is it a bad idea?

A collective answer is a quality mechanism. Several nodes answer the same prompt independently, reviewers cross-check the answers blind and twice with the positions swapped, and a synthesizer writes one text plus a list of disagreements. It is not verification, not mode 2, not chain consensus, and it never affects payment. The default is one node. The feature is opt-in, and the sheet shows which nodes read what: every answerer, every reviewer and a remote synthesizer can read the prompt. It costs at least as many answer sessions as there are answerers, plus review and synthesis, each an ordinary session. The client computes a multiplier from the prices you confirmed. That multiplier is not a fixed protocol constant. The sheet shows the total in ETH. It is a bad idea for a short lookup, for a latency-sensitive chat, for a prompt you do not want several operators to read, and whenever you wanted the single cheapest node. Mixing models often lowers average quality, and debate has cost 2.1–3.4 times the tokens of self-correction for equal or lower accuracy (evidence register §11, [V]). When one strong model is in a pool, the client suggests self-consistency first for a short checkable answer (a number, a choice or a label) or Self-MoA for free text. You may still opt into a collective answer. A plurality vote is never applied to free text. See [protocol/collective-answers.md](protocol/collective-answers.md).

### What happens when several nodes disagree?

The client labels the result contested when the splits list is non-empty or the agreement level is low, and it still shows the merged text. The splits list names each claim the answers disagree on, tied to stable anonymous ids assigned once for that request. An empty splits list is valid. A difference between the two position-swapped review passes is expected, and it does not by itself mark the synthesis incomplete. The synthesis is incomplete only when a required field is missing or malformed; then you see the raw answers and critiques. Disagreement does not reverse a signed voucher, does not slash anyone, and is not chain consensus. You can open every original answer. The default is one node. The collective-answer feature is opt-in, and the sheet shows which nodes read what. See [protocol/collective-answers.md](protocol/collective-answers.md).

### Can a big task be split into parallel sub-tasks on different nodes, and who sees what?

Only if you opt in to task decomposition. The feature is opt-in. The default is one node. A planner produces an off-chain plan: a DAG of waves, not a contract. Tasks in one wave have disjoint outputs and can run at the same time on different sessions. Later waves wait. A remote planner can read the full prompt. Each sub-task node sees its sub-task, which the client treats as containing prompt text unless the client has checked that the text contains none. A merge node is treated as able to read the prompt, because its inputs are assumed to quote it. A reviewer of a sub-task is treated the same way. The sheet shows which nodes read what before you sign, and it is shown again if the plan adds a node, widens a payload or raises a cap. Math, coding, Fermi estimates and tight writing stay on one node unless you override that (evidence register §12, [V]). The slowest task sets the wave's pace. See [protocol/orchestration.md](protocol/orchestration.md).

### Who assesses and plans, and who pays each planning, review and retry call?

Assessment starts on your device and does not contact a node. A remote planner, reviewer, merge or synthesizer runs only after you opt in, and only as an ordinary session you pay: one session per distinct pair of node and model id, at that offer's prices, plus L2 gas. The same rule pays a retry. A failed task may be retried once on a fallback node that was already on the confirmed sheet, as a new session; vouchers you already signed on the failed session stand. You pay both. Local planning and a local synthesizer add no remote inference payment. An optional orchestrator node, if you use one, is paid the same way and holds no session signer. Planner text cannot add a recipient or raise a cap by itself. The default is one node, the features are opt-in, and the sheet shows which nodes read what. See [protocol/orchestration.md](protocol/orchestration.md) and [economics/cost-and-pricing.md](economics/cost-and-pricing.md).

### Can one big model be split over several small machines?

Only as an experimental Phase 3 spike, and the reference client refuses it under mainnet parameters. It runs only with testnet-only, non-normative prices. In the cited settings, pipeline-sharded 70B-class models reach roughly 1–6 tokens per second, so the spike is slow (evidence register §10, [V]). Every shard holder can read the prompt, because activations have been inverted back to text in the cited work (evidence register §10, [V]). Shard holders, including the first and the last, hold no session and are not paid in v1 or in the spike. The client sits in the middle of every stage, so no holder needs another holder's keys. A lost holder restarts the generation from the beginning on a new chain from the sheet. Replaying cached stage inputs is measured as an option, with its latency and privacy cost, and no time or success rate is promised. The default is one node. The spike is opt-in, and the sheet shows which nodes read what. A cluster that one operator runs behind a single endpoint is a different thing: it is one node, one offer and one reader. See [node/distributed-execution.md](node/distributed-execution.md).

### Can small nodes speed up a big node with speculative decoding?

Local speculative decoding inside one node is an engine detail. It adds no reader, and it stays off in verifiable mode. Cross-node speculative decoding, where a draft node proposes tokens and a target node scores them, is an experimental Phase 3 spike. The reference client refuses it under mainnet parameters. Both the draft node and the target node can read the prompt. No WAN speed-up is promised: one preprint says that at wide-area round-trip times this kind of pipelined decoding does not beat co-located speculative decoding, the quote is what the preprint says (evidence register §9, [V]), and the result is not independently replicated (evidence register §9, [U]). Larger draft models raise α but cost more (higher c). The prompt is billed once per job, not once per round. Draft probability distributions are sealed metadata and are not billed as tokens. The spike is incompatible with verifiable mode. The default is one node, the spike is opt-in, and the sheet shows which nodes read what. See [node/distributed-execution.md](node/distributed-execution.md).

### What is an orchestrator node, and must I use one?

No. You do not have to use one. The orchestrator is open-source logic in the client SDK, and that is the default place it runs. An orchestrator node is optional, for a thin client. It is paid as an ordinary session for the tokens it generates when it plans, merges or synthesizes. It holds no session signer in v1, takes no cut, and cannot open your other sessions. Whenever it plans, merges or synthesizes, it can read the prompt, and the sheet counts it. The default is one node. Multi-node features are opt-in, and the sheet shows which nodes read what. Delegating your session signer to such a node is not part of v1. See [protocol/orchestration.md](protocol/orchestration.md) and [adr/0009-opt-in-client-orchestration.md](adr/0009-opt-in-client-orchestration.md).
