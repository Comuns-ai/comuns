## 1. Summary

Comuns is a community proposal for open-source decentralized LLM inference settled on Arbitrum One. Nothing described here runs yet, and no audit of any part of the design has been performed. This document answers one question: when a node is paid for inference, what can anyone check about what it did, and what does each check cost in privacy?

The honest answer is that v1 can prove much less than "the node ran the right model correctly". It separates six things that are usually blurred together and states which of them the evidence supports:

- **Payment authorization** — proven: every payment comes from a voucher signed by the session's `sessionSigner`, bounded by the session cap (docs/protocol/contracts-and-settlement.md).
- **Delivery** — proven: the client acknowledges each output chunk by signing the next cumulative voucher; a voucher covers only the prefix the client acknowledged, and a chunk the client never acknowledged is never paid.
- **Node identity** — proven: the node's registered key signs every input and chunk receipt, and the session names the node on-chain.
- **Model identity** — declared, not proven, in standard mode: the manifest in `ModelRegistry` names the model; nothing on-chain checks that the node loaded it.
- **Execution correctness** — not proven in standard mode; checkable only in opt-in verifiable mode by a second node that reads the prompt.
- **Subjective quality** — never proven by any mechanism in this document; a collective answer (docs/protocol/collective-answers.md) can improve it on some tasks but proves nothing.

The v1 assurance baseline is therefore: authenticated session binding, chunked cumulative vouchers, node-signed receipts, public reputation events, and an optional client-checked TEE attestation. **There is no economic slashing in v1.** No hash-mismatch penalty is permitted without a fully specified deterministic execution profile, an evidence format, an adjudicator and an appeal, and none of those exist. A dispute is a reputation event; the user's remedy is to stop signing vouchers. A signed voucher is never reversed.

**Verifiable mode (mode 2)** is opt-in re-execution: the user re-wraps the same prompt to a second, user-chosen node under a demonstrated deterministic profile and compares the two outputs. It is an integrity check, not a content-privacy mode: both nodes read the prompt, and it has no payment consequence in v1 even when the outputs differ. Both of its sessions are anonymous like any other — credit-funded and reached through a relay (ADR 0010, ADR 0011) — so the verifier should not learn who asked either. **Attested mode (mode 1)** is the content-private tier: this node should not be able to read your prompt; a physical attack on the hardware can break that (evidence register §14). It moves trust to the TEE vendors and has a documented physical-attack limit. Every other verification technique in the literature — activation commitments, random challenges, secret proxy tasks, optimistic and zero-knowledge proofs — is assessed in section 7 as a candidate for a later phase, with the conditions under which the evidence says it works, and Phase 3 may end with a published negative result.

## 2. Scope

In scope: what each party can verify about an inference job after the fact; the v1 baseline of receipts, vouchers and reputation; the definition of verifiable mode and the deterministic profile it requires; the client-side checks of attested mode; an assessment of verification candidates against the evidence register; the conflict between verification and privacy; an attack table; and the conditions a future penalty mechanism must meet before a CIP may adopt it.

Out of scope and owned elsewhere: the cryptography of envelopes, receipts and `outputCommitment` (docs/security/privacy-and-contexts.md); the contracts, the session state machine and the canonical `Voucher` type (docs/protocol/contracts-and-settlement.md); the threat catalogue (docs/security/threat-model.md); the node process and its engine backends (docs/node/node-design.md); the collective-answer mechanism, which is a quality aid and not verification (docs/protocol/collective-answers.md); and the model sharding and cross-node speculative decoding spikes (docs/node/distributed-execution.md), which appear here only in the assurance matrix and the attack table.

Evidence marks follow the register: **[V]** verified, **[L]** likely, **[U]** unsure; a claim not in the register is labeled UNVERIFIED. Mode names (`standard`, `attested`, `verifiable`), feature names (`collective_answer`, `cross_node_speculation`, `model_sharding`), the receipt and voucher fields and `outputCommitment` are the normative names of the referenced documents and are not redefined here.

## 3. What is and is not proven

The matrix below is the core of this document. Each row is a mechanism; the columns say what it proves, what it assumes, what it leaves unverified, and what it costs in privacy — counted, as the disclosure sheet counts it, in readers of the full prompt.

| Mechanism | Proves | Assumes | Leaves unverified | Privacy cost |
|---|---|---|---|---|
| Session binding (`openSessionFromCredit` or `openSession`, `sessionSigner`-signed job envelopes) | That the job was submitted by the client that funded the session, without saying who that client is; that payment goes to the node named on-chain; that no third party injected the job | The `sessionSigner` key is not stolen; the client is honest with its own user | Everything about execution | None beyond the executor |
| Node-signed input receipt `(sessionId, jobId, jobInputTokens, cumulativeInputTokensAfter)` | That the node counted the prompt and granted context with the pinned tokenizer to the same number the client computed, before any payment | The manifest's pinned tokenizer; the client recomputes locally | That the prompt was ever run (a node can redeem the input voucher and produce nothing; loss bounded by that prompt's input fee) | None |
| Node-signed chunk receipts plus cumulative vouchers | That each chunk the client paid for was delivered and acknowledged; a voucher covers only the prefix the client acknowledged, so the node's exposure is at most the one chunk it sent beyond that prefix, which stays unpaid if the client declines to sign | The client checks each receipt (model-token counts only, no metadata bytes) against the decrypted chunk with the pinned tokenizer | Which model produced the chunk; whether the text is correct or useful | None |
| `outputCommitment` = keccak256(`commitKey` ‖ `sessionId` ‖ `seq` ‖ `transcriptHash`) | A binding record of the delivered transcript that both parties can later open | Both parties keep `commitKey`, the transcript chain and the highest voucher until settlement — the node in persistent encrypted local storage, so that a restart can still redeem | Nothing on-chain checks it; opening it discloses the session's whole output to whoever receives it — it is never a proof without disclosure | None while closed; full output disclosure when opened |
| Registered model manifest (`modelId` = keccak256(`manifestHash`)) | Which weights, files and tokenizer the node *claims* to run; that the model's license permits paid hosting | Governance registered the manifest honestly | That the node loaded those weights (unverifiable in standard mode) | None |
| Public reputation events (volume, how sessions ended, user-recorded disputes) | That certain parties said certain things | Reputation consumers weigh verified requests more than self-reports | Everything; a reputation event proves nothing about any one job | None |
| Verifiable mode: re-execution by a user-chosen second node under a demonstrated deterministic profile; comparison of outputs | That two independently chosen nodes produced byte-identical output for the same input under the same profile — which makes silent model, precision or prompt substitution by one of them visible | A *demonstrated* deterministic profile (section 5); two operators that do not collude; the comparison is done by the client | Which of two differing outputs is wrong; anything about a job the user did not re-execute | **+1 full-prompt reader** (the verifier), by the user's explicit choice; the verifier's session is credit-funded and relayed, so it should not learn who asked |
| Attested mode: TEE quote verified client-side against a measurement list bound to the node build, the gateway and padding code and the model manifest | That a software stack with a known measurement loaded the named manifest inside a TEE, and that the node's job HPKE key and its `ohttpKeyConfig` were generated there | CPU and GPU vendor roots of trust; the attestation service; no physical access by the operator (TEE.fail, evidence register §14 [V]); no tokenizer side channel (TDXRay, evidence register §14 [L]) | Correctness of the model's output; retention after the job; anything a physical attacker can forge | None added: the plaintext exists only inside the TEE, and the operator should not be able to read it, barring a physical attack |
| TOPLOC-style activation commitment (candidate, section 7) | In the authors' tests, 100 % of model, prompt and precision changes were detected from commitments of 258 B per 32 tokens, with validation up to 100× faster than generation (evidence register §5 [V]) | A validator that re-runs prefill on the prompt; a backend with the integration (vLLM/SGLang, §5 [V]); thresholds tuned for GPU differences | Speculative decoding — it cannot detect it (§5 [V]); support on llama.cpp or mistral.rs is not claimed | The validator reads the prompt: **+1 full-prompt reader** |
| Collective answer (`collective_answer`, docs/protocol/collective-answers.md) | Nothing about weights or execution correctness; different models may legitimately disagree, so a disagreement is information, not evidence of fraud | k answerers, their reviewers and a synthesizer are honest readers | Everything verification would prove; it is a quality mechanism and is not mode 2 | **k full-prompt readers at least** (every answerer, every reviewer and a remote synthesizer) |
| Pipeline sharding (`model_sharding`, experimental) | Nothing: no shard holder can check another's layers, and the client cannot check any of them | Every shard holder is honest | Everything | Every shard holder reads the prompt in effect: inversion from activations recovers 92 % of 32-token inputs exactly, 88.4 % of tokens on a 65B model, and a 4,112-token medical prompt at 86.88 token F1 (evidence register §10 [V]) |
| Cross-node speculative decoding (`cross_node_speculation`, experimental) | Nothing about which draft model was used: draft substitution is not detected by TOPLOC (evidence register §5 [V]); no WAN speed-up is promised, since the cited preprint says the cloud round trip is too large for pipelined distributed speculative decoding to beat co-located speculative decoding at WAN round-trip times (§9, the quote is [V], the result is not independently replicated [U]) | The draft node and the target node are honest | Everything; incompatible with verifiable mode (section 5) | **+2 full-prompt readers** (draft node and target node) |

Three conclusions follow. First, v1 proves *who paid whom for what was delivered*, and nothing about *what ran*. Second, every mechanism that checks what ran needs a second reader of the prompt, so verification and privacy pull against each other (section 8). Third, the multi-node execution features add readers without adding verification: a collective answer, a sharded pipeline and a cross-node speculative pair each widen the reader set and prove nothing about weights or correctness.

## 4. v1 baseline

The v1 assurance baseline is the set of checks every session gets without opting into anything. All of it is already specified in the referenced documents; this section only collects it.

1. **Authenticated session binding.** A session is opened on-chain for one node, one model and one mode, with a `sessionSigner` fixed for its life. The reference client funds it with an anonymous credit through `openSessionFromCredit`, uses a fresh `sessionSigner` per session and reaches the node only through a relay (ADR 0010, ADR 0011); the binding proves which session a job belongs to, not who opened it. Every job envelope carries a `sessionSigner` signature over `(chainId, escrow address, sessionId, jobId, requestId, sheetVersion, keccak256(enc ‖ ciphertext))`, and the node rejects any envelope that does not verify against the signer recorded for that session. HPKE stays base mode; the signature is what stops third parties injecting jobs into someone else's session. `clientJobPublicKey` and every job parameter (`maxOutputTokens`, sampling settings) live inside the HPKE plaintext and inside that signature digest: nothing that changes the job travels in the clear.
2. **Chunked cumulative vouchers.** The one canonical EIP-712 type is `Voucher(bytes32 sessionId,uint64 seq,uint256 cumulativeWei,uint64 inputTokens,uint64 outputTokens,bytes32 outputCommitment,bool isFinal)` as defined in docs/protocol/contracts-and-settlement.md; this document uses the type by reference and defines no variant. Counts are cumulative for the session, `seq` starts at 1 and strictly increases, `cumulativeWei` is recomputed on-chain from the session's prices, and a later voucher can never lower what is owed. Payment is bounded by `min(depositWei, maxSpendWei)`. `isFinal` means only that the client closes the session; it is never the frame flag `endOfJob`.
3. **Node-signed receipts.** Before prefill, the node sends an input receipt `(sessionId, jobId, jobInputTokens, cumulativeInputTokensAfter)`; the client recomputes the input count with the manifest's pinned tokenizer, checks the cumulative total against `lastInputTokens + jobInputTokens`, and only then signs the input voucher. Every output chunk arrives with a receipt over the session-cumulative counts and the chunk hash, inside the sealed response frame; the client checks it against the decrypted chunk — counting model tokens only, never metadata bytes — and signs the next voucher. The voucher's `outputCommitment` binds the transcript under the session's `commitKey`, computed with that voucher's own `seq`. **Unsigned receipts bind nobody:** cumulative counts are the totals covered by the last voucher the client signed; a job whose input voucher the client never signed does not enter the counts, and the node's next input receipt starts from the last signed input total. A voucher may cover only the prefix the client acknowledged, and the node accepts it when its counts and `outputCommitment` match that prefix even if one more chunk is already in flight; that chunk is unpaid until the next voucher. A re-sent voucher whose `seq` and content equal the last accepted one is a no-op, never an error. A session runs its jobs one at a time (`maxConcurrentJobsPerSession = 1`), because receipts and vouchers form one chain per session.
4. **Pull payments, no slashing.** `redeemVoucher`, `closeWithVoucher` and `finalize` credit `balances[address]`; only `withdraw()` sends ETH. On a credit session nothing is credited to a user: settlement records the unspent remainder as `pendingWei`, which the client claims back as fresh notes with `claimChange` (ADR 0011). There is no slashing function, no dispute contract and no refund path for a disputed answer. A node's bond is withdrawable after its unlock delay and is never seized.
5. **Public reputation events.** Chain events (`VoucherRedeemed`, `SessionSettled`) and user-recorded off-chain events are the material for reputation systems that live outside the protocol. A dispute — "the answer was wrong", "the model was not what was advertised", "the verifier disagreed" — is recorded as a reputation event, and nothing else. Reputation consumers should weigh verified requests, not self-reported benchmarks (threat model T11).
6. **Optional client-checked attestation.** A node advertising `attested` presents a TEE quote that the client verifies before sealing anything (section 6). The check is client-side in v1.

**The dispute rule, stated once.** When a user believes a node misbehaved, the permitted v1 responses are exactly: stop signing vouchers (so no further chunk is paid), close the session unilaterally (`closeSession` on the contract, with no voucher — for a credit session submitted through a relay or broadcaster with a `sessionSigner` signature — then `finalize` after `closeDeadline`, which returns the unspent deposit: to the user's pull balance for a wallet session, as `pendingWei` for `claimChange` for a credit session; the node may redeem its highest non-final voucher while that is legal), and record a reputation event. The cooperative close — a final voucher signed by the client and `closeWithVoucher` by the node — is for the ordinary end of a session, not for a dispute. Vouchers already signed stand. No document, client or node may describe any outcome as a refund, a penalty or a slash, because no such mechanism exists and the conditions under which one could be fair (section 10) are not met.

**Why no hash-mismatch penalty.** It is tempting to say "if two nodes disagree, punish one". The evidence register records why that is unsafe today: 1,000 temperature-0 runs of the same Qwen3-235B model produced 80 unique outputs, and only batch-invariant kernels made outputs identical, at roughly 1.6× runtime on Qwen3-8B (evidence register §5 [V]). An honest node under ordinary serving conditions can therefore produce a different output from another honest node, and a penalty on mismatch would punish honesty. Until a deterministic profile is demonstrated, an evidence format fixed, an adjudicator named and an appeal defined, a mismatch is information for the user and nothing more.

## 5. Verifiable mode

**Definition.** `verifiable` (mode 2) is re-execution by a user-chosen second node under a demonstrated deterministic profile, followed by a comparison of the two outputs by the client. It is opt-in per request. It is the only v1 mechanism that can make model substitution visible, and it does so by disclosing the prompt to one more party chosen by the user.

**The deterministic profile.** A profile is an engine configuration a node declares for a model: pinned backend build, pinned model manifest, temperature 0, speculative decoding disabled, and fixed batching and kernel settings. Pinned versions, temperature 0 and disabled speculative decoding are **necessary but not sufficient** (evidence register §5 [V]: the 80-unique-outputs result was obtained at temperature 0). A profile counts as **demonstrated** only when reproducibility has been shown: repeated runs of a published test set give byte-identical outputs across every hardware and batching configuration the profile claims to support, and the test set, the outputs and the configurations are published so that anyone can repeat the demonstration. The register shows one route to such a profile — batch-invariant kernels, at roughly 1.6× runtime on the model tested (§5 [V]) — and no route is assumed to transfer to another backend, model or hardware class without its own demonstration. Phase 3 may find that no practical profile exists on the backends the network uses; that is an acceptable, publishable negative result.

**Rules of mode 2.**

- The user chooses the verifier node (node B) from the model's pool, exactly as the executor (node A) was chosen. Disclosure is explicit and consented: the disclosure sheet lists node B with role `verifier`, mode `verifiable`, `receives` = full prompt, its prices and its cap, and counts it in `readersOfFullPrompt`. **Never a random validator by default:** the protocol never picks the second reader for the user. The verifier is on the sheet **before** the user signs: adding a verifier to a request that was confirmed without one — including an orchestrated result the user later wants verified — creates a new sheet version that must be confirmed before any `openSession` or job under it.
- Both sessions are ordinary credit sessions opened with `openSessionFromCredit` in mode 2 on nodes that advertise it, each funded by its own note and each reached through a relay; the verifier is no exception to the anonymity default. Each node runs the same declared profile; a node that cannot produce the required profile for that model **refuses mode 2** (the request fails closed) rather than serving it in another configuration.
- The client re-wraps the prompt: a fresh HPKE envelope sealed to node B's registered key, under node B's own session, with its own `sessionSigner` signature, `clientJobPublicKey` and `commitKey`. Node A and node B never receive each other's envelopes, keys or outputs.
- **Comparison.** Both outputs return sealed to the client, which decrypts them and compares. The required check is the output comparison: the client hashes each complete output locally and compares the hashes, or compares the transcripts directly. Where a backend supports it, a **TOPLOC-style commitment** may be added: node A emits commitments to top-k activations every 32 tokens (258 B per 32 tokens) and node B validates them by prefill, up to 100× faster than generation in the authors' tests (evidence register §5 [V]). The integration exists for vLLM and SGLang (§5 [V]); **support on llama.cpp or mistral.rs is not claimed** by this document. Re-execution remains the required check; an activation commitment is at most an addition to it, never a substitute (it cannot detect speculative decoding, §5 [V]). **Who may receive a commitment.** Node B is a *disclosed* full-prompt reader — it is on the sheet, consented to and counted — so node A's activation commitments may be sent to node B, through the client, inside mode 2 and to that disclosed verifier only. The rule of section 8 that no activation commitment goes to a third party excludes disclosed verifiers; it forbids every other recipient.
- **No prompt-derived hash is ever posted publicly.** Comparison happens on the client; neither node, nor the chain, nor any third party receives a hash of the prompt or of the output (the disclosed verifier of the previous bullet is not a third party). The `outputCommitment` in each node's vouchers is keyed under that session's secret `commitKey` and reveals nothing.
- **`cross_node_speculation` is unsupported in mode 2.** The deterministic profile requires byte-identical output, which speculative engines do not guarantee (mistral.rs states that token-for-token equivalence is not guaranteed, evidence register §9 [V]), and TOPLOC cannot detect speculative decoding either (§5 [V]). A request that combines verifiable mode with `cross_node_speculation` **fails explicitly** with an error naming the conflict; the client never silently changes the requested mode, drops the feature, or downgrades to standard mode. Local speculative decoding inside one node is likewise disabled by the profile.
- **No payment consequence of a mismatch in v1.** Both nodes are paid for the tokens they delivered under their own vouchers. If the outputs differ, the client shows both, labels the result as a verification mismatch, and the user decides whether to stop signing with one or both nodes and whether to record a reputation event. The protocol does not decide which node was wrong: with two outputs and no adjudicator it cannot. A mismatch is therefore an input to reputation and to the Phase 3 evidence, never a refund, a penalty or a slash.
- Same-model integrity replication is verifiable mode and only verifiable mode. A collective answer, which compares different models, is not a verification (docs/protocol/collective-answers.md); a `task_decomposition` verify job that uses mode 2 for a sub-task is an ordinary mode-2 request for that sub-task.

```mermaid
sequenceDiagram
    participant U as User client
    participant A as Node A (executor, mode 2)
    participant B as Node B (verifier, mode 2, user-chosen)
    participant X as Comparison (client-side)
    U->>U: disclosure sheet: A and B both listed, readersOfFullPrompt = 2 nodes, user confirms
    U->>A: via relay · openSessionFromCredit (mode 2, own note) · HPKE envelope sealed to A, signed by sessionSigner_A, profile = deterministic
    U->>B: via relay · openSessionFromCredit (mode 2, own note) · same prompt re-wrapped: HPKE envelope sealed to B, signed by sessionSigner_B
    A->>U: input receipt; then chunks + chunk receipts (optional TOPLOC-style commitments on supported backends)
    B->>U: input receipt; then chunks + chunk receipts
    U->>A: cumulative vouchers per chunk (outputCommitment under commitKey_A)
    U->>B: cumulative vouchers per chunk (outputCommitment under commitKey_B)
```

**Verifiable mode is not a content-privacy mode.** Both nodes read the prompt and the answer, so content readers become two. Both sessions are credit-funded and relayed, so neither node should learn who asked. The mode is public on-chain. A mismatch has no payment consequence. Verifiable mode is not combined with attested mode in v1 (ADR 0010): a request asking for both is refused rather than served in one of them.

**What mode 2 proves and does not prove.** Identical outputs under a demonstrated profile mean that two independently chosen operators ran an equivalent computation on the same input, which makes silent substitution by either one visible unless they collude (attack table, section 9). It does not prove that the output is correct, useful or safe, and it says nothing about requests the user did not re-execute.

**Verifiable mode is visible.** A session's mode is public on-chain: `openSession` and `openSessionFromCredit` take `mode` and `SessionOpened` publishes it (docs/protocol/contracts-and-settlement.md). Two mode-2 sessions opened at the same moment can also be grouped with each other by timing, though not with the person who asked (threat model R10). A node therefore knows which of its sessions are mode-2 sessions, and mode-2 checks cover only those. An operator can run the advertised model under the declared profile for every mode-2 session and a cheaper model for ordinary traffic, and pass every check in this section. Mode 2 is an integrity check on the sessions it is used for, not a deterrent the executor cannot anticipate. The mitigation is **opt-in, unannounced client-side spot checks of standard-mode sessions**: at a time the user or the client chooses, the user re-runs a prompt sampled from past standard-mode requests on another node, under an ordinary session, and compares the outputs locally; that node reads the prompt and is disclosed on a sheet like any other reader, and the node that originally served the prompt is told nothing. A spot check inherits every limit of mode 2 — unless both runs were under a demonstrated profile, a difference cannot be told apart from nondeterminism; it proves nothing about the requests not sampled; it carries no payment consequence — and it is the most the v1 evidence supports.

## 6. Attested mode

`attested` (mode 1) is the content-private tier. It binds the executing software to a measurement rather than re-executing it, and it is anonymous like every other session. The claim, in the wording every client uses, is: this node should not be able to read your prompt; a physical attack on the hardware can break that (ADR 0010, evidence register §14). The cryptographic requirements are owned by docs/security/privacy-and-contexts.md; this section states what the client must check and what the check does not cover.

**Client-side checks, all required before sealing anything.**

1. **Quote freshness.** The client supplies a random nonce for each attestation; a quote whose report data does not include the client's nonce is rejected as replayed. For a long-lived session the client re-attests at a client-chosen interval and after any node key rotation (open question in the threat model).
2. **Key binding.** The quote is verified client-side, and its report data must commit, together with the client nonce, to the hash of the TEE-held job HPKE public key and to the node's `ohttpKeyConfig`. Both keypairs must be generated inside the TEE and never leave protected memory (ADR 0010), so that neither the OHTTP gateway nor the job envelope is opened outside it. A valid quote for an unrelated key proves nothing about the keys the client is about to seal to, so the client refuses to seal unless this binding verifies.
3. **Measurement list.** The measurement in the quote must appear on a published measurement list whose entries name the node build, the OHTTP gateway code, the padding code and the model manifest (`manifestHash`). The list is published by the project and maintained by CIP; the client refuses an unlisted measurement. The binding to the manifest is what gives attested mode its model-identity value: a measured build that loads an unlisted manifest does not match the list. Binding the gateway and padding code means a build that strips padding or logs requests before the job envelope is opened does not match either.
4. **Revocation.** The client checks the TEE vendor's collateral (certificate chains, TCB status) and refuses quotes from revoked or out-of-date platforms. Intel's EPID attestation and IAS were discontinued in April 2025, so DCAP or Intel Trust Authority are the remaining CPU attestation paths (evidence register §4 [L]). On the GPU side, NVIDIA's attestation service checks the GPU report together with the CPU TEE measurements and releases keys only after that (evidence register §14 [V]). The project's own measurement list is revocable by CIP.
5. **Fail closed.** If no eligible attested node exists, if the quote fails any check, or if any plaintext recipient on the disclosure sheet is not attested, the request fails closed; the client never silently downgrades to standard mode.

**What attested mode gives.** Content privacy from the operator, short of a physical attack: the prompt, the granted context and the answer are decrypted only inside the TEE. A remote or software-level compromise of the operator — a modified node binary that logs prompts, a swapped model file, a disabled retention rule, a gateway that strips padding — would change the measurement and fail the check.

**Overhead.** Current figures (evidence register §14): NVIDIA reports a confidential-computing overhead of 1–8 % [V, vendor]; an independent H100 + TDX study measured time-to-first-token up 21.8–27.8 % and throughput down 11.5–21.1 % [V]. An older dated snapshot (evidence register §4, 2026-10-12) records a different study: for an 8B model −6.85 % / −8.84 % throughput and +19–21 % time-to-first-token, for a 70B model roughly 0–2.3 % [V]. The figures come from different studies and setups and are not merged into one number.

**What it does not give.**

- **Residual hardware trust.** The user now trusts the CPU and GPU vendors' roots of trust and the attestation service, in addition to the operator's lack of physical access.
- **Physical-attack limit.** TEE.fail (S&P 2026) extracts TDX and SEV-SNP keys with a DDR5 interposer costing under $1,000; NVIDIA attestation reports are not VM-bound, so a report can be relayed; Intel and AMD consider physical attacks out of scope (evidence register §14 [V]). An operator with hands on the machine can forge a quote. Attested mode is protection against a remote or software-level compromise of the operator, never against the operator's own physical access (threat model T43).
- **Tokenizer side channel.** TDXRay (S&P 2026) recovers prompts from tokenizer memory-access patterns with 91.5–94.2 % similarity (evidence register §14 [L]). No mitigation is claimed in v1.
- **No output correctness.** A measured build can still produce a wrong answer. Attested mode is not combined with verifiable mode in v1 (ADR 0010); a user who wants a re-execution check uses mode 2 and accepts a second content reader.
- **On-chain verification is not v1.** The register puts a direct on-chain quote check at roughly 3M gas and a ZK-wrapped one at roughly 350k gas (§4 [V/L]); whether and who pays for it is an open question.

## 7. Candidates assessed

Each candidate is assessed against the register with its conditions preserved. "Phase 3" refers to the verification spike of the project charter, which may end with a published negative result for any of these independently.

**Replicated execution (full re-execution by a second node).** This is verifiable mode. It needs no new cryptography and no new contract: the verifier is an ordinary second session. Its cost is one more full execution and one more full-prompt reader, and it proves nothing without a demonstrated deterministic profile, because honest nodes can legitimately differ (80 unique outputs in 1,000 temperature-0 runs, evidence register §5 [V]). Status: v1 mechanism, opt-in.

**Deterministic profiles.** The precondition of everything else that compares outputs. The register records one demonstration: batch-invariant kernels made outputs identical at roughly 1.6× runtime on Qwen3-8B (§5 [V]). Open: whether such a profile can be demonstrated on the backends the network uses (docs/node/node-design.md), on the hardware classes the registry defines, and at a runtime cost operators will accept in a price band. Pinned versions, temperature 0 and disabled speculative decoding are necessary but not sufficient. Status: Phase 3 experiment; a negative result on a given backend means that backend cannot serve mode 2, not that mode 2 is redefined.

**TOPLOC (activation commitments).** Commits to top-k activations every 32 tokens (258 B per 32 tokens); validation up to 100× faster than generation; detected 100 % of model, prompt and precision changes in the authors' tests; tolerates GPU differences via thresholds; cannot detect speculative decoding; integrated with vLLM and SGLang (evidence register §5 [V]). Assessment: the cheapest known way for a verifier to check a long generation, because the verifier runs prefill rather than generation, but the verifier still reads the prompt, the thresholds are a tuning surface that an attacker may probe, and the method is blind to speculative decoding and therefore to draft substitution. This document does not claim support on llama.cpp or mistral.rs. Status: candidate addition to mode 2 on backends that support it; never a substitute for re-execution.

**PoSP/spML (random challenge).** A challenge with probability p; honest play is the unique equilibrium when p > C/((1−r)(R+S)); the analysis assumes deterministic execution (evidence register §5 [V]). The symbols are those of the cited work; this document assigns no values and does not redefine them. Assessment: this is the only candidate that gives a penalty mechanism a stated condition, and the condition contains a penalty term, which v1 has no way to impose and no adjudicator to decide. Its determinism assumption is the same unmet precondition as above. Status: the inequality is the test any future penalty CIP must satisfy (section 10), with values left unset; not a v1 mechanism.

**SVIP (secret proxy task).** The verifier gives the node a secret auxiliary task whose answer reveals whether the declared model ran [L]. Assessment: the register holds only a likelihood mark and no measured numbers, so no claim about detection rate or cost is made here. The proxy task still requires the verifier to know the prompt, and a node that learns the proxy construction can special-case it. Status: candidate for a Phase 3 literature check; no implementation planned.

**opML (optimistic, bisection to a one-step VM).** Disputes are bisected to a single step of a MIPS VM; a 7B model has been run on a CPU-only PC (evidence register §2 [V]); challenge window target under 10 minutes [L]. Assessment: recomputation inside the dispute exposes the prompt to whoever recomputes — the challenger, the on-chain verifier or both — adding readers the user did not choose and the disclosure sheet does not name; it needs a deterministic CPU execution path, which is the determinism precondition again, now on a CPU; and it presupposes a bond to forfeit, which v1 does not have. Status: not v1; a candidate only after a penalty CIP (section 10).

**zkML (zero-knowledge proofs of inference).** A 13B model proved in under 15 minutes [L]; a small model at roughly 174 tokens per minute [L]; Llama-3-8B at roughly 150 s per token [L] (evidence register §5). Assessment: the only candidate that would prove execution without disclosing the prompt to a second reader, and the only one that is not interactive at any of the cited rates. Its privacy value is exactly why it is worth watching. Status: not v1; revisited when the register records interactive rates.

**TEE attestation.** Section 6. Status: v1 mode 1, the content-private tier, with the physical-attack limit and the TDXRay side channel (evidence register §14 [V] and [L]).

**Economic slashing on staked executors.** Exists elsewhere — EigenLayer slashing is live [L], and some networks slash staked executors (evidence register §2 [V]). Assessment: a slash needs an adjudicable fact; without a deterministic profile, an evidence format, an adjudicator and an appeal, the fact "the node cheated" cannot be established well enough to take money, and a wrong slash punishes an honest operator with no recourse. Status: excluded from v1 by ADR 0004; conditions in section 10.

**Cross-model collective answers.** Several nodes running different models answer, cross-check blind and synthesize (docs/protocol/collective-answers.md). The register shows quality gains on some tasks — for example arithmetic 67.0 → 81.8 and MMLU 63.9 → 71.1 with three agents and two rounds (§11 [V]) — and quality losses on others, with correct answers destabilized by peers (§11 [V]). Assessment: a collective answer improves quality on some tasks and **proves nothing about correctness or about which model any node ran**; different models may legitimately disagree, so a disagreement is not evidence of substitution. It is **not mode 2**, it is not same-model integrity replication, and it is owned by docs/protocol/collective-answers.md. Status: v1 quality feature; not verification.

## 8. The verifier–privacy conflict

Every mechanism in sections 5–7 that checks what ran needs a party other than the executor to know the prompt: a re-executing node, a prefill validator, a challenger, a bisection recomputer. The only exception, zkML, is not interactive at the cited rates. The conflict is structural, not a design flaw to be engineered away, and this document resolves it by rule rather than by promise:

1. **Verification is opt-in and the verifier is user-chosen.** The user decides, per request, whether integrity is worth one more reader, and chooses who that reader is. The protocol never assigns a random validator, never samples requests for verification without a spot-check policy the user opted into (section 5), and never routes a prompt to a party the disclosure sheet did not name.
2. **The sheet counts the verifier.** `readersOfFullPrompt` includes the verifier by distinct node and distinct operator. A verifier run by the executor's operator is one operator, and the sheet shows it; such a choice gives no integrity and the client should warn.
3. **Nothing prompt-derived leaves the client.** Comparison is local. No hash of the prompt, no hash of the output and no activation commitment is posted on-chain or sent to a third party; `outputCommitment` is keyed and reveals nothing. **A disclosed verifier is not a third party:** inside mode 2 the executor's activation commitments may go, through the client, to the verifier the sheet names and the user confirmed (section 5), and to nobody else. Node receipts for chunks travel inside the sealed response frame, and any hash that must appear outside encryption is keyed, `keccak256(commitKey ‖ chunk)` (wire rules: docs/protocol/off-chain-api.md).
4. **Attested mode adds no reader.** It is the one integrity mechanism whose privacy cost is zero additional readers, at the price of vendor trust and the physical-attack limit. Users who cannot accept a second reader and cannot accept TEE trust have no integrity check in v1 beyond reputation. Cryptographic private inference (MPC or FHE) would remove the reader without a TEE, but evidence register §14 measures it at minutes per token and it is at most future work.
5. **The verifier is anonymous too, and still a reader.** The verifier is reached over a relay and funded by its own credit, so anonymity holds for both sessions while content readers become two. Verification never trades away who-asked privacy; it trades content privacy, and the sheet says so.
6. **Disputes do not open the transcript by default.** Opening `commitKey` discloses the session's whole output to whoever receives it. v1 has no adjudicator, so nothing requires a user to open it; a user who chooses to publish a transcript as evidence for a reputation claim does so knowingly and for that session only.
7. **A multi-node quality feature is not a verification feature.** `collective_answer`, `model_sharding` and `cross_node_speculation` multiply readers (k, every shard holder, two) and verify nothing; a user who wants integrity gets it only from mode 2 or mode 1, and only by paying the reader cost those modes state.

## 10. Path to a future penalty mechanism

A penalty mechanism — a hash-mismatch slash, a forfeited bond, a forced refund — is excluded from v1 and may be proposed later only by CIP, only after a published positive result, and only if every one of the following is specified in the CIP:

1. **A demonstrated deterministic execution profile** for every backend, model and hardware class the penalty would apply to, with the published test set and byte-identical results across the supported batching configurations (section 5). Pinned versions, temperature 0 and disabled speculative decoding are not enough.
2. **An evidence format**: exactly what a challenger submits — which inputs, outputs, commitments, receipts and keys — and what it discloses. Any format that opens `commitKey` discloses the session's whole output to the adjudicator, and the CIP must say so.
3. **An adjudicator**: who decides a dispute, with what computation, under what deterministic rule, and how the adjudicator itself is verified. An adjudicator that recomputes reads the prompt.
4. **An appeal**: how an honest operator contests a wrong finding before money moves, within what time, and who bears the cost of a failed appeal.
5. **The PoSP condition**: the mechanism must satisfy p > C/((1−r)(R+S)) in the sense of the cited work (evidence register §5 [V]), with the values of p, C, r, R and S stated in the CIP and justified from measured costs and the price bands in force; this document leaves every value unset. A mechanism that cannot state the inequality's terms cannot claim the honesty equilibrium.
6. **Fairness under nondeterminism**: a bound on the false-positive rate against honest nodes measured on the demonstrated profile, published before adoption.
7. **Contract scope**: any penalty needs new state-changing functions, which the closed list of 23 functions (ADR 0011 and docs/protocol/contracts-and-settlement.md) forbids without a CIP that amends that list; a slash on the registration bond also contradicts ADR 0004 and must supersede it explicitly.

Phase 3 is the experiment that produces the evidence for or against item 1 on the network's own backends, and separately for `model_sharding` and `cross_node_speculation`. A negative result for any of the three — no practical deterministic profile on the chosen backends; no privacy-preserving or performant sharding; no WAN speed-up — is an acceptable outcome, is published, and leaves v1 as specified here. Until a positive result is published, no Comuns document may describe a mismatch as anything but a reputation event.

## 11. Risks

### R1 — Model substitution is invisible in standard mode **[RISK] · High**

Nothing on-chain or in the protocol checks that the node loaded the manifest it advertised. The only responses are reputation and the opt-in modes, each of which costs the user something (a reader, or TEE trust). A user who never opts in has no integrity assurance beyond the operator's reputation. Because the session mode is public, an operator can serve mode-2 sessions honestly and substitute everywhere else; only unannounced client-side spot checks of standard-mode sessions (section 5) reach that traffic, and they are opt-in, sampled and bounded by the same determinism limits.

### R2 — No practical deterministic profile may exist on the network's backends **[RISK] · High**

Verifiable mode depends on a demonstrated profile, and the only demonstration in the register is on one backend and one model at roughly 1.6× runtime (§5 [V]). If Phase 3 cannot demonstrate a profile on the engines the nodes run, mode 2 is unavailable on those engines and the negative result is published; the proposal then offers no execution-correctness check besides attestation.

### R3 — Verification doubles the reader set **[RISK] · High**

Every check of output correctness needs a second prompt reader; attested mode does not check output correctness and adds no reader. Users who most need confidentiality are the users who can least afford verification, and the design does not resolve this; it only makes the trade explicit on the disclosure sheet.

### R4 — Colluding executor and verifier **[RISK] · Medium**

Output comparison cannot distinguish two colluding operators from two honest ones. Mitigation is the user's choice of verifier, the operator count on the sheet and a client warning when the verifier shares the executor's operator; none of these is a proof.

### R5 — A mismatch cannot be adjudicated **[RISK] · Medium**

With two differing outputs, v1 has no way to decide which node was wrong, and no refund follows. A user may pay two nodes for one request and learn only that they disagree. That is the stated price of having no slashing before the preconditions of section 10 are met.

### R6 — Attested mode defeated by physical access **[RISK] · High**

TEE.fail extracts TDX and SEV-SNP keys with a DDR5 interposer under $1,000 (§14 [V]), and TDXRay recovers prompts from tokenizer memory-access patterns (§14 [L]). An operator with physical access can forge a quote; attested mode must never be described as protection against the operator's physical access, and the client wording is: this node should not be able to read your prompt; a physical attack on the hardware can break that.

### R7 — Activation commitments blind to speculative decoding **[RISK] · Medium**

If TOPLOC-style commitments are added to mode 2, a node that re-enables speculative decoding despite the profile is not caught by the commitment (§5 [V]); the output comparison must remain the required check, and the profile must forbid speculative decoding independently.

### R8 — Input fee paid for a prompt that is never run **[RISK] · Low**

The node redeems the input voucher and produces nothing. Loss bounded by one prompt's input fee; remedy is to stop signing and record a reputation event; no refund exists in v1.

### R9 — Reputation events are unverified claims **[RISK] · Medium**

A reputation event proves that a party said something. A user can record a false dispute; a node can collect positive events from its own sessions. Reputation systems live outside the protocol and must weigh verified requests; nothing in v1 prevents reputation manipulation, and no mechanism here depends on reputation being accurate.

### R10 — Multi-node quality features mistaken for verification **[RISK] · Medium**

A user may believe that a collective answer "checks" the executor, or that a cross-node speculative pair "verifies" drafts. Neither does: a collective answer proves nothing about weights or correctness and different models may legitimately disagree; draft substitution is undetectable. Every client must label these features as quality or performance features and never as verification.

## 12. Open questions

1. **Deterministic profile format.** How a node publishes a profile (backend build hash, kernel settings, batching configuration, test-set hash and the demonstration results) so that a client can check that two nodes declare the same profile before opening two mode-2 sessions, and whether the profile hash should be part of the `modelBenchmarkHash` the node registers.
2. **Which backends can reach a profile.** Whether any of the Rust-native engines the node design considers, or llama.cpp or mistral.rs, can be configured for byte-identical output across the hardware classes, and at what runtime cost; the register's one demonstration is on a different stack (§5 [V]).
3. **TOPLOC-style commitments in mode 2.** Whether to add activation commitments on backends with the integration, how thresholds are chosen and published, and how they interact with the per-chunk receipts. The recipient is decided (section 5): commitments go through the client to the disclosed verifier only, and to no third party.
4. **Verifier selection UX.** How the client helps the user choose a verifier that is a different operator from the executor without the protocol choosing for the user, and how operator identity is established beyond the registered address.
5. **Spot-check policy.** How the client offers opt-in, unannounced spot checks of standard-mode sessions (section 5) as a user-configured policy — which past prompts are eligible, how the sample is drawn, how the second node is chosen and disclosed on a sheet, and how the result is shown — given that a mode-2 session is announced by its on-chain mode and cannot serve as an unannounced check.
6. **Quote freshness and re-attestation.** How often a client re-verifies a quote for a long session, whether re-attestation is required after node key rotation, and what happens to an open session whose node's measurement is revoked mid-session.
7. **Measurement list governance.** Who publishes and revokes the measurement list that binds node builds, gateway and padding code to manifests, under which CIP process, and how a reproducible build is established for each listed measurement.
8. **Evidence from Phase 3.** What the published result of the verification spike must contain — test sets, outputs, configurations, failure rates — so that a later penalty CIP can cite it under section 10, and what form a negative result takes.
9. **Opening `commitKey` for a reputation claim.** Whether a standard format exists for a user who chooses to publish a session transcript as evidence, so that the disclosure is explicit, scoped to one session and never required.
10. **zkML watch condition.** At what proving rate and cost a zero-knowledge check becomes worth a Phase 3 experiment, given that it is the only candidate that adds no prompt reader.
