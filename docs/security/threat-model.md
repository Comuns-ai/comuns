## 1. Summary

Comuns is a proposal for open-source decentralized LLM inference settled on Arbitrum One with Rust nodes. Nothing runs yet and no audit of any part of the design has been performed. This document lists what the proposal must protect, who could attack it, what each party can see, and what the v1 design does about each threat. It is deliberately blunt about the central limit. In standard mode the executing node reads the prompt, the granted context and the answer in plaintext, because an executor must see plaintext unless FHE, MPC or a TEE is used (evidence register §4 [L]). Anonymity means that this node and chain observers are not supposed to learn who asked, and attested mode is the tier where the node should not be able to read your prompt either, barring a physical attack (evidence register §14).

What v1 does defend is the boundary around that chosen party and the link to the person asking: the node sees the prompt but not the client's network address, because every request goes through an Oblivious HTTP relay run by a different registered party (ADR 0010); the chain sees a session funded by an anonymous credit, not by the user's wallet (ADR 0011); a context is identified by its own key, not by a wallet (ADR 0012); nobody else decrypts (two-way HPKE), nobody else can submit work to the user's session (every job envelope is signed by the session's `sessionSigner`), the user knows exactly how many nodes and operators will read the prompt before paying (the disclosure sheet), nothing widens that set silently (fail-closed and re-show rules), and escrowed funds can only be spent through vouchers the session signer actually signed. Multi-node execution features multiply readers; the design's answer is not to hide this but to count it, show it, and bind the user's confirmation into every envelope.

## 2. Scope

In scope: the confidentiality and integrity of prompts, completions and contexts; the anonymity of the asker towards nodes, relays and chain observers; the keys that protect them; the escrow and voucher flow that pays for inference, including the credit pool, change and ragequit of ADR 0011; relays and their bonds; node bonds; the integrity of the model weights a node claims to run; and availability of the settlement path. Both single-node execution and the multi-node execution features defined in docs/security/privacy-and-contexts.md are covered.

Out of scope: see section 7. Mitigations referenced here are specified in docs/security/privacy-and-contexts.md (cryptography, modes, disclosure sheet), docs/protocol/contracts-and-settlement.md (escrow, vouchers, bonds), docs/security/inference-verification.md (verifiable and attested mode), and ADR 0010, ADR 0011 and ADR 0012 (relays, anonymous credits, contexts without a wallet link). Where this document and ADR 0011 disagree on a function signature or a parameter name, ADR 0011 wins.

## 3. Assets

| Asset | Why it matters | Where it lives |
|---|---|---|
| Prompt | The user's question and any pasted material; often the most sensitive thing in the system | Client; selected node(s) in plaintext during execution (inside the TEE in attested mode) |
| Identity of the asker | Who sent a request: the client's network address, wallet, devices and anything that ties sessions to one person; the property the default tier exists to protect (ADR 0010) | Client; the relay sees the network address only; nobody else should hold it |
| Deposit-to-session linkage | Which public `depositNote` funded which session, change note or ragequit; if recovered, the wallet that deposited is linked to the node, model and mode it paid for | Nowhere by design; inferable from timing, amounts and identity reuse (T33, T34) |
| Note secrets | The client-generated Semaphore identity behind each deposit or change note; spending a note needs it, and a lost secret loses the note | Client, stored durably before the commitment is published; nowhere else |
| Completion | The answer; may restate the prompt | Node during generation; client |
| Context | Transcripts, documents, system prompts, versioned and reused across requests | Client; owner-chosen host (ciphertext); granted node (plaintext during a job) |
| Client identity HPKE secret | Unwraps every context version key `K_v` the client owns; the backup export (identity key plus every key-wrap record, no ciphertext) is what restores the keys on a new device | Client, encrypted at rest; encrypted backup file |
| Client per-job HPKE secret | Decrypts the completion of one job | Client, in memory for the job |
| Session commit key `commitKey` | Random 32-byte key per session; keys the `outputCommitment` of every voucher of the session; opening it discloses the session's output | Client and node, until the session is settled; sent once, sealed in the session's first job envelope |
| Context version keys `K_v` | One per context version; open exactly that version | Client; wrapped to the identity key beside the ciphertext and in the backup export; wrapped to granted nodes |
| Context ciphertext | The only copy of a version's content; neither the registry (hashes only) nor the backup (keys only) can recreate it | Client device; owner-chosen host or second device, if any |
| Node HPKE secret(s) | Decrypt every request sealed to the node; a keyring holds every key of an unsettled session | Operator machine, encrypted at rest; inside the TEE in attested mode |
| Ethereum keys (user, operator, relay operator) | The user's wallet deposits notes and is public at `depositNote`, `ragequit` and the `withdraw()` of a ragequit balance only; operator keys authorize registry entries and bond withdrawals | Wallets |
| Context signing key | One random key per context; `contextId = keccak256(contextPubKey)`; signs every head record, never the wallet key (ADR 0012) | Client, in the local vault and the identity-key backup |
| Session signer key | Fresh per session; signs every job envelope, every voucher up to the session cap, the credit-session close and `claimChange` | Client application |
| Escrowed ETH | Unspent notes in the credit pool, the open value of every session, `pendingWei` awaiting change, and wallet-funded deposits | Chain, in `SessionEscrow` |
| Node and relay bonds | The operators' stakes in `NodeRegistry` | Chain |
| Weight integrity | Whether the node runs the model it advertises | Node |
| Availability | Whether users can get answers and nodes can get paid | Nodes, sequencer, RPC providers |

## 4. Actors

| Actor | Capability | Trust in v1 |
|---|---|---|
| User | Owns prompt, contexts and notes; chooses nodes, modes and features | Trusted with own data; may run a compromised client |
| Chosen operator | Runs the selected node and its OHTTP gateway; reads plaintext in standard mode; should not learn who asked | Trusted with content by the user's choice in standard mode; paid; bonded |
| Relay operator | Forwards the OHTTP request; sees the client's network address, request and response sizes, timing and the target gateway; never the envelope | Untrusted for content; must not be a node operator: the contract refuses one address in both roles, and two addresses of one person are not detected (T31, T32); bonded; paid `relayFeeWei` |
| Broadcaster | Submits `openSessionFromCredit`, a credit-session `closeSession`, `claimChange` or `setContext` on the client's behalf; sees what it submits and its own network peer | Untrusted; can delay or drop, cannot redirect a spend, because the contract computes the bound message itself |
| Credit pool observer | Reads every `depositNote`, spend, settlement, change insertion and `ragequit` from the chain | Untrusted; the adversary of T33 and T44 |
| Trusted-setup participants | Contributed to the Groth16 setup of the Semaphore v4 circuit (more than 400, evidence register §15 [V]) | Trusted collectively: one honest participant is assumed; a compromised setup could forge spends (T42) |
| Other operators | Run unselected nodes; observe the chain and possibly the network | Untrusted; see ciphertext only |
| Sequencer | Orders Arbitrum One transactions; single sequencer with roughly one day to force inclusion [V] | Untrusted for confidentiality; semi-trusted for liveness |
| RPC provider | Serves chain reads and relays transactions; the reference client reaches it through a relay for every session-specific read (T40) | Untrusted; user-chosen |
| Network observer | Sees traffic sizes and timing on the client-to-relay and relay-to-node hops | Untrusted |
| Context host | Stores context ciphertext and signed head records; accepts a new version by compare-and-swap | Untrusted for content; trusted for availability and, while the context is not anchored on-chain, for sequencing (ADR 0012, T41) |
| Verifier (verifiable mode) | User-chosen second node that receives the full prompt and re-executes it under a demonstrated deterministic profile; reached through a relay and funded by its own credit | Trusted as a second plaintext reader; should not learn who asked |
| Planner or assessor node (any feature, including task decomposition) | Receives the full prompt to decompose or assess it | Trusted as a plaintext reader and counted as a full-prompt reader; its plan is data |
| Sub-task node or sub-task reviewer (task decomposition) | Receives sub-task text that may quote the prompt | Counted as a full-prompt reader unless the client verified its payload contains no prompt text |
| Peer answerer (collective answer) | Receives the full prompt; answers independently | Trusted as a plaintext reader |
| Reviewer or synthesizer (collective answer, parallel planning) | Receives the prompt plus all anonymized answers or plans, and for the synthesizer all critiques | Trusted as a plaintext reader; may bias the synthesis |
| Merge node (task decomposition) | Receives all sub-task outputs it merges; assumed to quote the prompt | Counted as a full-prompt reader |
| Optional orchestrator node | Receives the full prompt whenever it plans, merges or synthesizes, and the plan when the user delegates planning | Trusted as a plaintext reader; holds no session signer in v1 |
| Session injector | Any party that can reach a node's endpoint and knows a public `sessionId` | Untrusted; stopped by the `sessionSigner` envelope signature |
| Shard holder (model sharding, experimental) | Receives activations of a layer range | Treated as a full-prompt reader (evidence register §10) |
| Draft node (cross-node speculation, experimental) | Receives the prompt; produces draft tokens | Treated as a full-prompt reader |
| Target node (cross-node speculation, experimental) | Receives the prompt plus draft tokens | Trusted as a plaintext reader; can substitute drafts undetectably |
| Physical attacker | Has hands on a node machine | Defeats attested mode (TEE.fail, evidence register §14 [V]) |
| Malicious weights | A model that leaks or misbehaves by construction | Not detectable by the protocol |
| Compromised client | Wallet extension, SDK or dapp under attacker control | Defeats every client-side guarantee |

## 6. Threats and v1 response

Each entry gives the threat, then the v1 response. Where the response is "none" the document says so.

**T1 — Ciphertext replay.** An attacker replays a captured request envelope to the same or another node, or replays a completion frame into another job, hoping to make a node re-execute a prompt or a client accept stale output. *Response:* the AAD binds `chainId`, the `SessionEscrow` address, `sessionId`, `jobId`, `requestId`, sheet version, `planId`, `taskId`, `role`, `contextId`, `contextVersion`, direction and frame sequence number, with an `endOfJob` last-frame flag; replays and truncations fail AEAD verification or sequence checks and are rejected. Replay into another session is additionally stopped by the envelope signature of T25.

**T2 — Model substitution.** The node runs a cheaper model than the `modelId` it was paid for. *Response:* invisible on-chain in standard mode. Mitigated by operator reputation and bonds, and by opt-in verifiable mode, in which a user-chosen second node re-executes the request under a demonstrated deterministic profile and the outputs are compared, at the cost of a second plaintext reader. Draft substitution in cross-node speculation is a special case, see T21.

**T3 — Dishonest token counts.** The node reports more tokens than it produced or consumed. *Response:* input and output are bounded separately. Input: before prefill the node sends a node-signed input receipt `(sessionId, jobId, jobInputTokens, cumulativeInputTokensAfter)`; the client checks `jobInputTokens` against its own tokenization of this job's prompt and granted context with the tokenizer pinned in the model manifest, checks `cumulativeInputTokensAfter = lastInputTokens + jobInputTokens`, and signs the input voucher — which carries the cumulative total — only if both hold, so an inflated input count, for this job or smuggled into the running total, is never paid. Output: the client checks each chunk's node-signed receipt (session-cumulative counts and the chunk hash) against the chunk it decrypted, signs cumulative vouchers one chunk at a time, and refuses to sign beyond what it received; the node can over-claim at most the chunk the client declines to sign. The residual that remains, stated plainly: the node can redeem the input voucher and never run the prompt; the loss is bounded by that prompt's input fee, the remedy is to stop signing and record a reputation event (R13). Automatic signing checks counts, not quality (T8).

**T4 — Abandoned session.** The node or the client disappears mid-session. *Response:* the node redeems only vouchers the session signer actually signed; every payment and refund is credited to an internal balance and collected with `withdraw()`, so a wallet that cannot receive ETH can never lock funds. If the client disappears, its last voucher is almost always non-final, and `closeWithVoucher` rejects a voucher whose `final` is false, so the node never relies on it: the node redeems its highest non-final voucher with `redeemVoucher` while that is legal (`open`, or `closing` before `closeDeadline`), then calls `closeSession`; `finalize` after `closeDeadline` credits the remainder `depositWei − settledWei` to the user, and `finalize` itself pays the node nothing, which is why the redemption must come first. The node is owed nothing beyond its last voucher. If the node disappears, nothing refunds automatically: the user calls `closeSession` and then `finalize` after `closeDeadline`, and the unspent deposit is credited for withdrawal. A node that disappears is still paid for the work the client acknowledged, as long as it redeems while the session is `open` or `closing` before `closeDeadline`. Either the user or the node may call `closeSession` at any time; nothing closes a session automatically, so a session both parties abandon stays `open` with its deposit until one of them does (T30). A credit session has no user address (ADR 0011): instead of the user, any broadcaster presenting a `sessionSigner` signature over `(chainId, escrow, sessionId, "close")` may call `closeSession`, and settlement credits nothing to a user but records `pendingWei = depositWei − settledWei`, which the client turns into fresh notes with `claimChange` (T38).

**T5 — Sequencer outage.** The single Arbitrum sequencer stops including transactions; force inclusion takes roughly one day [V]. *Response:* vouchers stay redeemable while the session is `open`, or `closing` before `closeDeadline`; `CLOSE_WINDOW` must exceed an expected outage plus about one day of force inclusion; docs/protocol/contracts-and-settlement.md owns the value. Nodes should redeem promptly, since `redeemVoucher` is allowed at any time while legal. Residual risk, with no guarantee offered: an outage that starts shortly before `closeDeadline` can still cost a node its unredeemed vouchers (R8).

**T6 — Stolen session signer key.** Malware on the client obtains the `sessionSigner` key. *Response:* the key can sign job envelopes and vouchers up to the effective cap `min(depositWei, maxSpendWei)` for sessions it is registered to, until the session is settled. `closeSession` does not stop it: vouchers stay redeemable until `closeDeadline`, so a thief can hand the node a voucher for the whole cap during the close window. There is no signer rotation or revocation in v1 (open question 2). The mitigation is small per-session caps, which is why caps are shown on the disclosure sheet and summed as `totalCapWei`.

**T7 — Hostile RPC provider.** The RPC lies about chain state: a wrong node key, a wrong registry entry, a wrong context hash. *Response:* the RPC is user-chosen, and the client may use several and compare. An RPC cannot decrypt content sealed to an honest node's key, but a hostile RPC can redirect an unpinned client to an attacker-controlled record, which exposes the client's later standard-mode content to that attacker. The client therefore reads `hpkePublicKey` and `ohttpKeyConfig` only from the latest `NodeRegistered` or `NodeUpdated` event in its own relay-tunnelled chain view, may compare independent RPCs, and pins node keys across sessions. The `key_probe` of ADR 0015 (proposed) checks that the live gateway holds the registered keys before the spend; it does not stop this threat, because an attacker who registered a key it holds passes the probe. *Residual:* a client whose every chain read comes from the hostile RPC, and that has no pinned key for the node, can be directed to an attacker's record.

**T8 — Automatic voucher signing pays for garbage.** The client signs vouchers as frames arrive; a node that streams nonsense gets paid. *Response:* none in v1 beyond the cap and reputation. Automatic signing checks token counts, not answer quality. A user who wants quality assurance opts into verifiable mode.

**T9 — Operator legal compulsion.** An operator is ordered to hand over prompts or to log them. *Response:* none that the protocol can offer in standard mode; the operator reads plaintext. The no-logging policy is a policy, not a protection. Attested mode raises the bar to a build-measured node but does not defeat an operator who has physical access (T10). Users choose operators by jurisdiction at their own judgement.

**T10 — TEE physical attack.** An operator or intruder with physical access uses a DDR5 interposer to extract TDX or SEV-SNP keys including attestation keys, and can undermine GPU confidential-computing attestation (TEE.fail; dated evidence register §4 snapshot [L]; current claim evidence register §14 [V], see T43). *Response:* none; vendors treat physical attacks as out of scope (evidence register §14 [V]). Attested mode is documented as protection against a remote or software-level compromise of the operator, never against the operator's own physical access.

**T11 — Benchmark proxying.** A node answers verification or benchmark requests by forwarding them to a stronger model or a different machine, then runs something cheaper for real traffic. *Response:* verifiable mode on real requests, chosen by the user without notice to the node, is the only check; reputation systems should weigh verified requests, not self-reported benchmarks.

**T12 — Key loss.** The user loses the client identity HPKE key or its backup, or the only device holding a context's ciphertext; the operator loses the node key. *Response:* every context version key `K_v` is wrapped to the identity key, and the backup export contains the identity key and every key-wrap record, so restoring it on a new device restores the keys of every version whose ciphertext can still be fetched from a context host or a second device. The backup holds no ciphertext: a context stored only on a lost device is gone even with the backup, and the recommendation is at least one host or a second device for ciphertext. Losing both the key and the export loses every context, permanently. A node key loss means a registry update; sessions sealed to the old key cannot be served, and nothing refunds them automatically. The node first redeems its highest non-final voucher with `redeemVoucher` while that is legal. For a credit session, the reference path, `closeSession` is then called by the node or, with a `sessionSigner` signature, through a relay or broadcaster, and `finalize` after `closeDeadline` records `pendingWei = depositWei − settledWei`, which the client claims as fresh notes with `claimChange` (T4). Only on the non-reference wallet `openSession` path does either party call `closeSession` and `finalize` credit the remainder to the user's pull balance for `withdraw()`. `closeWithVoucher` is used only if the client had already signed a voucher with `final` set, never otherwise.

**T13 — Prompts pasted into public issues.** Users or operators paste prompts, contexts or decrypted frames into issue trackers, logs or chat when debugging. *Response:* client and node redact content from error output by default; the contributing guidelines must forbid including prompt material in issues. This is a process control, not a technical one.

**T14 — Multi-node execution features multiply readers.** `collective_answer`, `task_decomposition`, `parallel_planning`, `model_sharding` and `cross_node_speculation` each add nodes that read the prompt or parts of it. *Response:* bounded by the disclosure sheet and the user's signature. Every non-empty feature set is opt-in per request; the sheet lists every recipient with its roles and `receives` array; `readersOfFullPrompt` counts distinct nodes and distinct operators, is derived from the actual payloads, and treats the named reader list as a floor, never a ceiling — any remote assessor or planner in any feature, and any sub-task executor or reviewer whose payload contains prompt text (assumed unless the client verified otherwise), is counted; `requestId` and sheet version are bound into every envelope's AAD; a pool that cannot fill the confirmed set fails closed.

**T15 — Disclosure sheet skipped or under-counted.** A client (buggy, forked or malicious) omits the sheet, shows a stale one, or counts fewer readers than it actually sends to. *Response:* the sheet is a client-side control, so a compromised client defeats it. Mitigations: open-source reference clients, a conformance test that replays the client's envelope log against the sheet it displayed, and the AAD binding, which makes an under-counted sheet detectable after the fact by anyone holding the log. No on-chain enforcement exists, because `executionFeatures` is never stored on-chain.

**T16 — Planner-induced over-disclosure.** A planner node writes a plan that routes more of the prompt into sub-tasks than needed, for example by quoting it wholesale into every sub-task, so that nodes meant to see a fragment see everything. *Response:* the plan returns sealed to the client; the sheet is re-shown before execution sessions when a planner ran first, with the `receives` array of every sub-task node reflecting what the plan actually sends; the remote planner or assessor is always counted as a full-prompt reader, a merge node is always counted as one (its inputs are assumed to quote the prompt), and a sub-task node or sub-task reviewer is counted as one unless the client has verified that the payload it will seal contains no prompt text — the default assumption is that it does. The user can reject the plan. The client must compute `counts` and `readersOfFullPrompt` from the plan's actual payloads, not from the planner's claims; the reader list in docs/security/privacy-and-contexts.md section 8 is a minimum, never a ceiling.

**T17 — Prompt injection through intermediate results.** A sub-task output or a peer answer contains text that tries to instruct the merge node, the synthesizer, the orchestrator node or the client — to change recipients, raise caps, open sessions or exfiltrate the prompt. *Response:* intermediate text is data, never authority over recipients or spending. Recipients and caps come only from the confirmed sheet; the client re-seals only approved parts; no node holds a session signer except the client; the orchestrator node holds none in v1. A node that acts on injected instructions can at most produce a bad answer within its own cap.

**T18 — Colluding peer or reviewer biases the synthesis.** In `collective_answer` an answerer and a reviewer, or the synthesizer itself, collude to suppress a correct answer. *Response:* the synthesizer must list the splits among answers and critiques rather than silently choosing, and the client shows each original answer to the user alongside the synthesis. Anonymization of answers before review reduces, but cannot remove, collusion by operators who recognize each other's style.

**T19 — Stale consent.** Between the user's confirmation and transmission, the node, model, data scope or cap of some recipient changes — a node rotates its key, a pool reassigns, a plan grows. *Response:* any such change invalidates the sheet before transmission; the client must re-show and obtain a new confirmation with a new sheet version; a funded session never implies consent to a new request, and a request that reuses open sessions still gets its own sheet and confirmation. Envelopes carry the sheet version in the AAD so that no envelope can be attributed to an outdated confirmation.

**T20 — Shard holders invert prompts from activations.** In `model_sharding` every shard holder receives activations. The evidence register §10 records that text embeddings can be inverted to recover 92 % of 32-token inputs exactly [V], that a malicious participant in split inference recovers the prompt from received activations at 88.4 % token accuracy on a 65B model [V], and that a 4,112-token medical prompt was nearly fully inverted (86.88 token F1) from a middle layer, with four practical defenses failing [V]. *Response:* sharding never offers more privacy than standard mode; every shard holder is treated and counted as a full-prompt reader on the disclosure sheet; activations move only between the client and each sheet-listed holder, through a relay, OHTTP-encapsulated to that holder's registered `ohttpKeyConfig` without the inner job HPKE envelope, never holder to holder, and the sheet says so; there is no direct client-to-holder connection, and holders stay unpaid volunteer readers; the feature stays an experimental Phase 3 spike. v1 nodes do not use llama.cpp's RPC backend, whose documentation calls it a proof of concept, fragile and insecure, and says never to run it on an open network (evidence register §10 [V]).

**T21 — Cross-node speculative decoding.** In `cross_node_speculation` both the draft node (which receives the prompt to draft) and the target node (which receives the prompt plus the drafts to verify them) read the full prompt, since both drafting and verifying require it. Draft substitution — the target accepting drafts from a different model than advertised — is undetectable by TOPLOC (evidence register §5 [V]). *Response:* both nodes are counted as full-prompt readers; the feature is incompatible with verifiable mode, because verifiable mode is re-execution under a demonstrated deterministic profile that needs byte-identical output, which speculative engines do not guarantee (mistral.rs states that token-for-token equivalence is not guaranteed, evidence register §9 [V]), and TOPLOC, a candidate checker, cannot detect speculative decoding either; it stays an experimental Phase 3 spike. "Speculation at a Distance" states that at WAN round-trip times the cloud round trip remains too large for pipelined distributed speculative decoding to beat co-located speculative decoding (evidence register §9, the quote is [V], the result is not independently replicated [U]), so no WAN speed-up is promised.

**T22 — Orchestrator node sees the prompt when it plans, merges or synthesizes.** A user who delegates planning to an orchestrator node gives it the full prompt and the resulting plan; an orchestrator node that merges or synthesizes receives prompt text through the material it combines. *Response:* the orchestrator node is listed on the sheet with role `orchestrator node` and a `receives` array naming the full prompt and, when planning is delegated, the plan, and it is counted as a full-prompt reader in every one of those roles; it is paid through an ordinary session; its only authority is that session — it holds no session signer, cannot open sessions for the user and cannot add recipients; the plan it produces returns sealed to the client and is subject to T16 and T19.

**T23 — Context grant misuse.** A node granted a context for versions a–b tries to read other versions, keeps the keys past expiry, or passes them to another node. *Response:* every context version has its own key `K_v`, and a grant wraps exactly the keys of the versions it names, so a node granted versions 5–6 holds nothing that opens version 4 or version 7, whether it obtains their ciphertext from the host or anywhere else; the grant names the range, an `expiresAt` in unix seconds and the hash of the node key it was wrapped to; later versions are unreadable to a revoked node because their keys were never wrapped to it; a node that already decrypted the granted versions cannot be made to forget them, and the design says so. Passing a key to another node is a policy violation that the protocol cannot detect in standard mode.

**T24 — Wrong-key sealing through a registry race.** A client seals to a node key that was rotated between its read and the node's receipt. *Response:* the node keeps a keyring of every HPKE key used by any session that is not yet settled, however many rotations have happened since, and deletes a key only after every session that used it is settled, so a second rotation never strands a session opened under the first key; the AAD includes the session, so a node cannot serve an envelope it cannot decrypt and the client retries after refreshing the registry.

**T25 — Job injection into an open session.** HPKE base mode does not authenticate the sender, and `sessionId`, `chainId` and the escrow address are public from `SessionOpened`. A third party opens TLS to the node, seals an envelope to its registered key under the victim's `sessionId` with its own `clientJobPublicKey`, and would get the prompt executed and returned to it while the victim's own envelope for that `jobId` fails the sequence check. *Response:* every job envelope carries a signature by the session's `sessionSigner` over `(chainId, escrow, sessionId, jobId, requestId, sheetVersion, keccak256(enc ‖ ciphertext))`; the node rejects any envelope whose signature does not verify against the `sessionSigner` recorded on-chain for that session, before decrypting or scheduling it. HPKE stays base mode; the signature is what stops third parties injecting jobs into someone else's session.

**T26 — Low-entropy output recovered from the chain.** An observer hashes the possible answers of a yes/no or classification prompt and compares them with what the voucher commits to on-chain. *Response:* `outputCommitment = keccak256(commitKey ‖ sessionId ‖ seq ‖ transcriptHash)`, where `commitKey` is a random 32-byte key the client generates for the session and sends sealed inside the session's first job envelope, kept by client and node until the session is settled and known to nobody else, and `transcriptHash = keccak256(prev ‖ chunkHash)` is chained from zero over every output chunk of every job in the session; without `commitKey` no candidate answer can be tested. Because the key is per session rather than per job, every voucher of a multi-job session commits under the same key to one chain. The commitment is not checked on-chain, and opening `commitKey` to anyone discloses the session's whole output to them; it is a binding record, never a proof without disclosure.

**T27 — Price change between confirmation and inclusion.** The operator calls `updateNode` with a changed in-band price — one wei is enough — after the user confirmed the sheet and before `openSession` is included, hoping the session copies the new price, or hoping to force the client onto an abort path that locks the deposit for `CLOSE_WINDOW` on every attempt. *Response:* `openSession` takes `expectedPriceInPerMillion` and `expectedPriceOutPerMillion`, the confirmed sheet's prices, and reverts if the node's current offer for that model differs, so a changed offer yields a reverted transaction and no session: no deposit is ever locked by an offer change, and the operator can at most cost the user the gas of a revert. As defence in depth, after inclusion the client still reads the prices copied into the session and, if they differ from the confirmed sheet, signs nothing and calls `closeSession`, recovering the deposit through `finalize` after `closeDeadline`. A price change, like a changed node, model, data scope or cap, invalidates the sheet.

**T28 — Context version race or head-only registry.** Two devices of one owner publish the next version at once, or a node is asked to verify a version that is no longer the head. *Response:* under ADR 0012 the default path is the context host's compare-and-swap on `version == head + 1` over signed head records chained by `prevContentHash`, and the optional on-chain anchor `setContext` applies the same rule; either way one next version wins; the losing write is refused (a reverted transaction when anchored), the losing client keeps its local edit, rebases on the new head and publishes the next version, and nothing is silently merged or dropped. A node verifies an older granted version against its signed head record and the `prevContentHash` chain, or, when the context is anchored, against its `ContextSet` event, so a grant that is not the head still verifies. Host equivocation and stale backups are T41. `contentHash` is keccak256 of the complete stored blob, one definition for everyone.

**T29 — Manifest squatting.** Anyone registers a model manifest, or marks a model as commercially hostable, to capture a name or mislead operators. *Response:* `registerModel` and `updateModel` are callable only by the governance timelock through CIPs in v1; with nobody seated there is no mainnet registration, and Sepolia models come from a testnet-only CIP.

**T30 — Open deposit with a lost wallet or an absent counterparty.** A session stays `open` because neither party calls `closeSession`: the user's wallet is lost, or the node is gone and the user never returns. *Response:* either the user or the node may call `closeSession` at any time, and nothing closes a session automatically; the close window therefore starts only when one of them acts, and until then the deposit sits in the escrow at no one's disposal. A node that wants its earnings follows T4: redeem the highest non-final voucher, call `closeSession`, and after `closeDeadline` anyone may call `finalize`, which credits the remainder to the user's address. If the user's wallet is lost, that credited balance is unrecoverable — pull payments go to the user's address and `withdraw()` pays only its caller — and the design says so rather than pretending otherwise. For a credit session the equivalent loss is the `sessionSigner` key: without it nobody but the node can close the session and nobody can claim its change, and if both the node and the key are gone the session stays open (ADR 0011). An anyone-can-close idle timeout is an open question (section 9), not part of v1.

**T31 — Relay and node in one registration.** One address registers as both a relay and a node, or a client is steered to a relay that is the node itself, so the gateway learns the client's network address together with the prompt. *Response:* `registerRelay` reverts if the caller is a registered node or relay, `registerNode` reverts if the caller is a registered relay, and `openSessionFromCredit` reverts when `relay == node` (ADR 0011). The reference client picks a relay at random from the registry, refuses a relay equal to the node, has no direct client-to-node job path, and fails closed when no relay is available (ADR 0010). Oblivious HTTP itself holds only if relay and gateway are run by different entities (evidence register §15 [V]). *Residual:* the check is on addresses; see T32.

**T32 — Two-address Sybil.** One person registers a relay under one address and a node under another, or many of each to raise the chance of being chosen for both hops, and so sees the client's network address and the prompt of the requests it carries end to end. *Response:* none that the contract can enforce. There is no personhood or operator-identity check, and two addresses are two registrations (ADR 0010). Random relay choice across the whole registry, and a relay bond of at least `MIN_RELAY_BOND_WEI` (named, unset), raise the cost of many registrations without preventing them. A user may also place the relay behind Tor; that is a client choice, not the default (ADR 0010). Shipping precedents rely on relays run by distinct, named third parties (Apple Private Cloud Compute: Cloudflare and Fastly, evidence register §15 [V]); Comuns has no equivalent arrangement. *Residual:* a Sybil operator holding both hops learns who asked for those requests (R17).

**T33 — Deposit-to-spend timing and amount linkage.** `depositNote` is public and signed by the depositor's wallet. A credit pool observer correlates the time and denomination of a deposit with the next `openSessionFromCredit` in that group, a change note spent right after its session settled, or a public `ragequit`, and links the wallet to the node, model and mode it paid for. Evidence that this works on deployed pools: one study reported that address reuse and fund-flow links traced 5.1–12.6% of Tornado Cash withdrawals and that FIFO timing added 15–22 percentage points, but v3 of that paper was withdrawn over reference errors, so these figures are cited only with that caveat; mixer anonymity sets shrink 27.34% on average on Ethereum and advertised sizes are mostly inaccurate (evidence register §15 [V]). Refund amounts are a known re-linking channel (evidence register §15 [V]). *Response:* fixed denominations, so an amount reveals only the group; the spend is submitted by the node or a broadcaster, never by the deposit wallet; a fresh identity per note (T34); no variable refund — change comes back as fixed-denomination notes and the dust below the smallest denomination goes to the node (ADR 0011); a client-side delay between deposit and spend and before spending change, both unset; the client shows the group size (T44). *Residual:* a user who deposits and spends at once, or who is nearly alone in a group, is linkable; `ragequit` is public and linkable by design; the delays have no values yet (R18).

**T34 — Note identity reuse.** A client reuses one Semaphore identity for two notes. With a fixed scope per group, one identity has one nullifier per group, so the second note in the same group is unspendable, and the same commitment appearing in two groups links them publicly. *Response:* every note, deposit or change, gets a fresh client-generated identity whose secret is stored durably before the commitment is published; `SessionEscrow` keeps `noteSeen[commitment]`, and `depositNote` and `claimChange` revert on any commitment already seen in any group (ADR 0011). The check does not rely on LeanIMT's duplicate-leaf behaviour, which is UNVERIFIED. *Residual:* a client that loses a note secret loses that note; there is no recovery and no admin.

**T35 — Identifying prompt text and stylometry.** In standard mode the node reads the prompt, and names, addresses, account numbers or a writing style can identify the author regardless of the transport. LLMs infer personal attributes from text at up to 85% top-1 accuracy [L], an LLM pipeline linked pseudonymous profiles at up to 68% recall at 90% precision [V], and a public query log identified AOL user 4417749 [L] (evidence register §16). *Response:* the client warns that the node can read the prompt and that identifying content defeats anonymity; it cannot prevent it. Attested mode narrows who can read the text to the TEE, within the limits of T43. *Residual:* anonymity in standard mode does not survive identifying content. No study of splitting a conversation across sessions to resist this was found (evidence register §16 [U]), and no such mitigation is claimed (R19).

**T36 — Size and timing side channels with padding unset.** The relay, a network observer and the node see request and response sizes and inter-frame timing. Whisper Leak, across 28 LLMs, often reached more than 98% AUPRC, and padding, batching and packet injection reduce it but none fully protects; token lengths alone let attackers reconstruct 29% of responses and infer the topic of 55%; unpadded ciphertext length leaks request and response size (evidence register §16 [V]); output length alone reveals the language with more than 75% precision (evidence register §14 [V]). *Response:* job envelopes and streamed frames are padded to size buckets and output tokens are batched per frame (ADR 0010); the bucket and batch sizes are unset. *Residual:* until values are set and measured, no reduction is claimed, and even then the mitigation reduces and does not remove the leak; the relay can combine a topic guess with the client's network address (R20).

**T37 — Relay–node timing correlation and chunked-OHTTP round trips.** A relay and a node that collude, or one observer of both hops, correlate the timing and volume of a request on each side; in chunked OHTTP the interactive exchange also lets the relay or the gateway measure round-trip time (evidence register §15 [V]), which hints at the client's distance. The reference shape follows the draft's section 7.2 guidance: no request chunk depends on a response chunk within one exchange, which also avoids in-exchange replay of interactively generated request chunks (evidence register §15, recheck 2026-10-15, [V]). The gateway still links a session's exchanges through the session fields inside them and can time the gap between a response and the client's next exchange, which includes the client's round trip; that cross-exchange timing remains a residual (R8, T37, RR-40). Timing side channels were found in a shipping IP-blinding relay that "may be able to unmask" users, exploitability Low (NCC Group, evidence register §16 [V]); another shipping design states that timing and volume metadata are not protected (evidence register §16 [V]); DeepCorr reports 96% flow-correlation accuracy from about 900 packets (evidence register §15 [L]). *Response:* relay and node are distinct registrations (T31); padding and batching (T36); one `ohttpKeyConfig` per node for every user, so no user can be handed a unique key (ADR 0010). *Residual:* correlation by a colluding pair or by an observer of both hops is not prevented, and no figure is claimed for how often it succeeds (R17).

**T38 — Stolen session signer claims the change.** Malware obtains a credit session's `sessionSigner` key. Besides the vouchers of T6, it can sign `claimChange` with commitments it controls, taking the session's `pendingWei` as notes, or sign a close. *Response:* `claimChange` requires a `sessionSigner` EIP-712 signature over `(chainId, escrow, sessionId, keccak256(changeCommitments), keccak256(denominationIndexes))` and is callable by anyone with no deadline while `pendingWei > 0`, so the thief and the honest client race; the reference client claims change promptly after settlement, through a relay or broadcaster. The key is fresh per session, so a theft reaches one session, and the loss is bounded by that session's denomination, vouchers and change together. *Residual:* no signer rotation or revocation exists (open question 2); a thief with the key and a head start wins the race (R6).

**T39 — The node refuses or front-runs a credit spend.** The client hands the node, or a broadcaster, a spend proof for `openSessionFromCredit`. The recipient withholds it or submits it later, or someone who sees the pending transaction submits it first. *Response:* the contract computes the message `keccak256(node, relay, modelId, mode, sessionSigner, expectedPriceInPerMillion, expectedPriceOutPerMillion)` and the scope itself (ADR 0011), so a front-runner can only open exactly the session the client asked for, at its own gas cost. A withheld proof consumes nothing; the client can spend the same note elsewhere with a new proof, after which the withheld one reverts on the stored nullifier. A proof also stops verifying once its root has been replaced for longer than `MERKLE_TREE_DURATION` (named, unset). A proof submitted late, while still valid, opens a session the client may no longer want; the client calls `closeSession` with its `sessionSigner` signature, then `finalize` after `closeDeadline`, which sets `pendingWei` — the full denomination when nothing was settled — and then `claimChange`; `closeSession` alone does not set `pendingWei`. A changed price makes the spend revert, as in T27. *Residual:* delay and gas griefing; a node that never submits can deny service but cannot take the note.

**T40 — Chain reads link a network address to a session.** The client looks up its own session, voucher, settlement and change events and fetches Merkle witnesses and roots; an RPC provider or indexer that sees the client's network address querying one `sessionId` or one commitment links that address to the session. *Response:* every session-specific chain read by the reference client goes through the same anonymity-preserving transport as the jobs — RPC or indexer queries tunnelled through a relay — and an indexer is a backend behind that transport, not an alternative to it (ADR 0010). The deposit transaction itself is public and wallet-linked anyway (T33). *Residual:* an RPC provider that is also the relay or a node falls under T32 and T37; a read issued right after a deposit can still be correlated by timing.

**T41 — Context pseudonym linkage and host sequencing.** A `contextId` is a stable pseudonym. Nodes that receive grants for the same context can link the sessions that use it; an on-chain anchor links that context's versions; turns within one conversation are linkable by design, as in the shipping precedent (evidence register §16 [V]). With the chain no longer the default anchor, the context host is trusted for sequencing as well as availability: it can equivocate between two devices that have never compared checkpoints, and a device restored from a stale backup accepts a head that a newer device would reject until the two sync. *Response:* no wallet appears in the context record, the AAD or the grant; the context key is random and never derived from the wallet; `setContext` is submitted by a broadcaster or a node, never by the user's wallet; the client can fork a context under a new key, at the cost of a new pseudonym with no history; the disclosure sheet's `anonymity.contextLinkage` states which linkage applies; clients persist accepted head checkpoints in the vault and the backups and reject rollback behind them; an anonymous public anchor is required whenever a globally consistent multi-device head is promised (ADR 0012). *Residual:* linkage within a context is accepted; a fork can still be linked to its parent by shared plaintext and timing; equivocation against unsynced devices is a documented limit (R23).

**T42 — Trusted-setup, circuit or verifier flaw.** Spends rely on Groth16 proofs whose soundness depends on the Semaphore v4 trusted setup, the circuit and the verifier contract. A compromised setup or a circuit or verifier bug would let someone forge membership proofs and spend notes that were never deposited — for example by opening sessions to a node they control. The original 2024 setup had more than 400 participants [V]; the production artifacts and the verifier key points come from the 2025 Binary Merkle Root Fix ceremony [V], run after an under-constrained ZK-Kit circuit bug fix, whose participant count, close date and final beacon were not found in the sources examined on 2026-10-15 [U]; per-file artifact hashes were not found in the sources examined on 2026-10-15 [U] (evidence register §15, recheck 2026-10-15). *Response:* `SessionEscrow` calls only the stateless Semaphore v4 Groth16 verifier and keeps its own trees, nullifiers and root window instead of a shared deployment's `validateProof`, which has no access modifier (evidence register §15 [V], ADR 0011). Semaphore v4.0.0 was audited by PSE and v3 by Veridise (evidence register §15 [V]); no audit claim transfers to the Comuns wrapper, which has none. The escrow is non-upgradeable, so no key can rescue or seize notes. *Residual:* a forged spend is indistinguishable on-chain from an honest one and the pool has no recovery; a defect is fixed by a new deployment that users migrate to by ragequit or by spending down (R21).

**T43 — Physical and side-channel attacks on attested mode.** The attested-tier claim is: this node should not be able to read your prompt; a physical attack on the hardware can break that. TEE.fail (S&P 2026) extracts TDX and SEV-SNP keys with a DDR5 interposer costing under $1,000, NVIDIA attestation reports are not VM-bound and can be relayed, and Intel and AMD consider physical attacks out of scope (evidence register §14 [V]). TDXRay (S&P 2026) recovers prompts from tokenizer memory-access patterns with 91.5–94.2% similarity (evidence register §14 [L]). Battering RAM and WireTap are further physical attacks (evidence register §14 [L]). *Response:* the client verifies the quote before sealing; the quote binds the TEE-held job HPKE key and the `ohttpKeyConfig`; the measurement list binds the node build, the gateway and padding code and the model manifest; the request fails closed on any failed check, and when any plaintext recipient on the sheet is not attested (docs/security/inference-verification.md section 6, ADR 0010). This extends T10. *Residual:* a forged or relayed quote cannot be told apart from an honest one by the client, and no mitigation for TDXRay is claimed (R5).

**T44 — Small anonymity sets at launch with no adopted minimum.** At launch there are few relays, few nodes and few notes per denomination, so a spend, a change note or a request hides among few others. No authoritative minimum anonymity-set size was found (evidence register §15 [U]), and advertised mixer anonymity sets were mostly inaccurate (evidence register §15 [V]). *Response:* the client shows the group size it can observe and warns below a threshold that the CIP sets; the disclosure sheet shows the sizes it can observe and claims no minimum (ADR 0010, ADR 0011). *Residual:* no threshold is adopted, and early users are the least protected (R18).

**T45 — A credit holder pays a node it operates.** There is no dedicated anonymous withdrawal entry point. A credit holder who operates a node can open a session to it, sign vouchers and withdraw that node's balance, because the contract does not verify that inference happened. Regulatory classification is UNVERIFIED and is a Phase 4 review item (facts in evidence register §16, not legal advice). *Response:* none in the contract; deposits and `ragequit` stay public, and `ragequit` pays only the caller and never more than that address deposited into the group (ADR 0011). *Residual:* the exit through a self-operated node exists by construction (R22).

**T46 — Unregistered relay or direct client connection.** Someone opens TLS to the gateway without being a registered relay with `unlockAt == 0`, or as the node's own operator, or a client connects to the gateway directly, so that the node could learn a client's network address together with the prompt, or serve an exchange that no registered third party carried. The gateway's "registered relay" rule had no mechanism before ADR 0014. *Response:* ADR 0014 (proposed): on every TLS connection the relay presents an operator-signed EIP-712 delegation and a per-connection signature over the gateway's fresh, connection-bound, single-use nonce; the gateway checks in its own chain view that the recovered operator has a relay record with `unlockAt == 0` and is not the node's own operator, and serves nothing, not even the capability document, on a connection that has not passed; the relay checks the gateway's challenge against its own registry view before signing; the reference client has no direct path to a node and fails closed when no relay is available (ADR 0010). The exchange carries no client data. *Residual:* one person running a relay and a node from two addresses passes, because the check is on registry roles, not persons (T32, R17).

## 7. Out of scope

- Jailbreaks and prompt attacks on the model's own behaviour.
- Content moderation and the legality of prompts or outputs.
- Training-data leakage by the model itself (memorized text surfacing in completions).
- Cryptographic private inference (MPC or FHE): evidence register §14 measures it at minutes per token, and it is at most future work.
- Regulatory classification of the credit pool, relays and nodes; it is a Phase 4 review item, and the facts in evidence register §16 are not legal advice.
- Denial of service against individual nodes, beyond noting that the user can choose another node.
- Correctness of the Arbitrum One rollup and its fraud-proof system.

## 8. Risks

### R1 — Executor reads plaintext in standard mode **[RISK] · High**

Inherent in standard mode (evidence register §4 [L]): the executing node reads the prompt, the granted context and the answer. Anonymity hides who asked, not what was asked. Attested mode is the tier where the node should not be able to read your prompt either, barring a physical attack (evidence register §14), within the limits of R5.

### R2 — Activation inversion in model sharding **[RISK] · High**

Prompts are recoverable from activations at 88.4 % token accuracy and 86.88 token F1 in the cited settings (evidence register §10 [V]). Sharding is counted as full disclosure to every shard holder and stays experimental.

### R3 — Disclosure sheet skipped or under-counted **[RISK] · High**

The sheet is the only thing standing between the user and an unbounded reader set, and it is enforced client-side. A buggy or hostile client removes the control entirely. Mitigation is open source, conformance testing and AAD binding for after-the-fact detection.

### R4 — No audit **[RISK] · High**

No audit has been performed on this design, on any implementation, or (per its own documentation) on the `hpke` crate the implementation would use [V]. Everything in section 6 is a design intention.

### R5 — TEE physical and side-channel attacks **[RISK] · High**

TEE.fail extracts TDX and SEV-SNP keys with a DDR5 interposer under $1,000 (evidence register §14 [V]); TDXRay recovers prompts from tokenizer memory-access patterns (evidence register §14 [L]). Attested mode cannot be sold as protection against an operator with physical access (T10, T43).

### R6 — Stolen session signer with no rotation **[RISK] · Medium**

Loss bounded by `min(depositWei, maxSpendWei)` per session, but `closeSession` does not stop the thief: vouchers stay redeemable until `closeDeadline`, and on a credit session the thief can also race the client for the change (T38). No rotation or revocation in v1; small caps, one denomination per credit session and a fresh signer per session are the only mitigations.

### R7 — Orchestrator node sees the prompt when planning is delegated **[RISK] · Medium**

Delegated planning adds a full-prompt reader with influence over the plan, and an orchestrator node that merges or synthesizes is a full-prompt reader too. Its authority is limited to its own session, and the plan is shown and re-confirmed, but the reader is real.

### R8 — Sequencer outage versus `closeDeadline` **[RISK] · Medium**

A `CLOSE_WINDOW` shorter than outage plus roughly one day of force inclusion [V] lets honest nodes go unpaid, and even a sufficient one cannot save a node whose outage begins shortly before `closeDeadline`; prompt redemption is the node's own defence, and no guarantee is offered.

### R9 — Prompt injection through intermediate results **[RISK] · Medium**

Bounded to bad answers within a cap because intermediate text has no authority, but a node that follows injected instructions still wastes the user's deposit for that session.

### R10 — Metadata correlation of multi-node requests **[RISK] · Medium**

Several credit sessions opened at one time — a verifier pair, the recipients of a collective answer or a decomposed task — can be grouped by timing even though no payer is recorded, and the group reveals the request's shape. No v1 mitigation.

### R11 — Model substitution in standard mode **[RISK] · Medium**

Invisible on-chain; only reputation, bonds and opt-in verifiable mode respond.

### R12 — Grant revocation does not reach decrypted data **[RISK] · Low**

Understood and documented; short `expiresAt` and narrow ranges limit exposure, and per-version keys make a narrow range cryptographically binding rather than a policy.

### R13 — Input voucher paid for a prompt that is never run **[RISK] · Low**

The node redeems the input voucher and produces nothing. Loss bounded by one prompt's input fee; the remedy is to stop signing and record a reputation event. No refund exists in v1.

### R14 — Price change between confirmation and inclusion **[RISK] · Low**

Bounded by `openSession` reverting when the current offer differs from the expected prices it was given, and, as defence in depth, by the client's check of the copied prices after inclusion and its refusal to sign; the user pays the gas of a reverted `openSession`, and an operator who changes prices on every attempt can keep a user from opening a session with that node, but never lock a deposit.

### R15 — Open deposit nobody closes, and a lost user wallet **[RISK] · Medium**

Nothing closes a session automatically. A credit session, the reference path, stays `open` until the node, or a relay or broadcaster carrying a `sessionSigner` signature, calls `closeSession`; `finalize` after `closeDeadline` then records `pendingWei = depositWei − settledWei` for `claimChange`, and if both the node and the `sessionSigner` key are gone the session stays open (T4, T30). On the non-reference wallet `openSession` path, a deposit whose user and node both go silent stays `open` until one of them calls `closeSession`, and when the user's wallet is lost the balance credited to the user's pull balance by `finalize` or `closeWithVoucher` is unrecoverable, because pull payments go to the user's address. Mitigation in v1: small per-session caps and prompt closing; an anyone-can-close idle timeout is an open question.

### R16 — Context ciphertext kept on one device **[RISK] · Medium**

The backup export restores keys, not ciphertext; a context stored only on a lost device is lost with it, backup or not. Mitigation: at least one context host or a second device holding the blobs, recommended by the client at context creation.

### R17 — Relay–node collusion and two-address Sybils **[RISK] · High**

Nothing on-chain stops one person from running a relay and a node under two addresses, and a colluding relay and node, or an observer of both hops, can correlate timing (T32, T37). Where that happens, the default anonymity property fails for the requests concerned.

### R18 — Deposit-to-spend linkage and small anonymity sets **[RISK] · High**

Deposits are public and groups are small at launch; timing and amount heuristics have linked a share of withdrawals on deployed pools, with the caveat that v3 of the cited paper was withdrawn (evidence register §15 [V]). No minimum set size and no delay value is adopted (T33, T44).

### R19 — Identifying prompt content and stylometry **[RISK] · High**

In standard mode the node reads text that can identify its author (evidence register §16). Anonymity of transport and payment does not protect a user who identifies themselves in the prompt (T35).

### R20 — Size and timing side channels with padding unset **[RISK] · Medium**

Bucket and batch sizes are unset, and the cited evidence says padding and batching reduce but do not remove topic inference (evidence register §16 [V], T36).

### R21 — Proof-system or credit-accounting flaw **[RISK] · High**

A trusted-setup compromise, a circuit or verifier bug, or an accounting bug in the relay split, the dust branch or the root window could drain or freeze the non-upgradeable pool, and no external review of the Comuns wrapper exists (T42).

### R22 — Regulatory classification of the credit pool **[RISK] · Medium**

A credit holder can exit through a node it operates (T45). Regulatory classification is UNVERIFIED and is a Phase 4 review item (facts in evidence register §16, not legal advice).

### R23 — Context pseudonym linkage and host equivocation **[RISK] · Medium**

Sessions that grant the same context are linkable by `contextId`, and an unanchored context relies on the host for sequencing, with equivocation against unsynced devices and stale-backup acceptance as documented limits (T41).

## 9. Open questions

1. **Minimum `CLOSE_WINDOW`.** What outage duration the minimum should assume beyond the roughly one-day force-inclusion delay [V], and whether it should be a protocol constant or a per-session choice with a floor.
2. **Session signer rotation or revocation.** Whether a later CIP should let the user replace or revoke the `sessionSigner` without settling the session, since `closeSession` does not stop a stolen signer, and what that does to voucher monotonicity and to the envelope signature check of T25.
3. **Sheet conformance enforcement.** Whether any part of the disclosure sheet can be made verifiable by a third party without storing `executionFeatures` on-chain — for example a commitment to the sheet hash in `openSession`.
4. **Collusion resistance in collective answer.** Whether operator diversity (distinct operators, not just distinct nodes) should be a hard requirement for reviewers and the synthesizer rather than a displayed count.
5. **Attested-mode quote freshness.** How often a client must re-verify a quote for a long-lived session, and whether the node must re-attest after a key rotation.
6. **Experimental spikes.** Whether `model_sharding` and `cross_node_speculation` should be removed from the feature set entirely until the privacy and performance evidence (evidence register §10, §9, §5) changes, rather than carried as spikes.
7. **Reporting channel.** Which disclosure process applies to a vulnerability found in a node or client before any audit exists; SECURITY.md owns the answer.
8. **Anyone-can-close idle timeout.** Whether a later CIP should let any address call `closeSession` on a session idle for longer than some bound, so that a deposit abandoned by both parties (T30) eventually settles, and what that does to a node that is merely slow to redeem. Not in v1.
9. **Lost first envelope.** How the node and client recover if the session's first job envelope, which carries `commitKey`, is lost before the node acknowledges it, without opening a new session; docs/security/privacy-and-contexts.md open question 9.
10. **Relay operator diversity.** Whether relays should come from a short list of distinct, publicly known operators, as in the shipping precedents (evidence register §15 [V]), and how that could be expressed without a seated authority, given that the contract only sees addresses (T32).
11. **Anonymity thresholds and delays.** Which minimum group size the client should warn below, and which deposit-to-spend and change delays it should apply, given that no authoritative minimum was found (evidence register §15 [U]) (T33, T44).
12. **Padding buckets and batch sizes.** Which values to adopt and how to measure what they leave, given that the cited evidence shows reduction without full protection (evidence register §16 [V]) (T36).
